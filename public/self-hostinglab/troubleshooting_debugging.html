01 // Kesedaran Realiti Operations

Kenapa Troubleshooting Penting?

Server Sempurna Tidak Wujud

Dalam dunia realiti, apa-apa sistem yang berjalan akan mengalami gangguan. Sama ada Raspberry Pi di rumah atau server Cloud bertaraf enterprise, failure adalah pasti.

Rule #1: Failure is not IF, but WHEN.

10 Punto Kegagalan Biasa:

Network DNS Firewall Application Docker Tunnel Database Disk Full Internet ISP Config Typo

"Skill server bukan hanya membina. Skill server juga ialah membaiki."

02 // Konsep Asas Diagnosis

Symptom vs Root Cause

Symptom (Gejala) Apa yang user nampak
"Website tak boleh dibuka!" / 502 Bad Gateway

Symptom hanyalah isyarat luar. Merawat symptom tanpa mencari punca tidak akan menyelesaikan masalah.

Root Cause (Punca Sebenar) Apa yang berlaku di belakang
• DNS Record salah IP DNS Layer
• cloudflared process mati Tunnel Layer
• Docker container exited (OOM) Container Layer
• Port 8080 terikat di 127.0.0.1 sahaja Network Binding
SYMPTOM (Gejala)
POSSIBLE CAUSES (Siasatan)
ROOT CAUSE (Punca Bukti)
03 // Framework Kerja

Mental Model Troubleshooting

1. OBSERVE
Apa sebenarnya berlaku?

Kumpul mesej error, HTTP status code, dan symptom terkini.

2. TEST
Apa bukti yang dikumpul?

Jalankan command spesifik (ping, curl, ss, status, logs).

3. ISOLATE
Layer mana bermasalah?

Pasti kan sama ada masalah Local, Network, Tunnel, atau App.

4. FIX
Betulkan punca secara terkawal

Lakukan perubahan berfokus pada root cause yang ditemui.

5. VERIFY
Pastikan pulih sepenuhnya

Uji semula request dan pastikan tiada kesan sampingan.

6. DOCUMENT
Catat penyelesaian

Tulis nota kejadian (Post-Mortem) supaya tidak berulang.

04 // Peraturan Emas

Golden Rule Troubleshooting

"Ubah SATU perkara pada satu masa."

Pendekatan Panik (CARA BURUK)

❌ Tukar DNS + Restart router + Reinstall Docker + Tukar firewall secara serentak

Kesan buruk: Anda tidak akan tahu perubahan mana yang menyelesaikan masalah atau menambah kerosakan baru!

Pendekatan Berstruktur (CARA BAIK)

1. Check DNS resolution
2. Check Local Network Reachability
3. Check Port & Service Binding
4. Check Container / Application Logs
"Kalau ubah semuanya serentak, kita tak tahu apa yang sebenarnya menyelesaikan masalah."
05 // Arsitektur Diagnosis

Troubleshooting Layers (Stack 1-8)

LAYER 8: DATABASE — MySQL / PostgreSQL / Redis Connection & Queries
LAYER 7: APPLICATION — Python Flask/FastAPI, Node.js Code Execution
LAYER 6: CONTAINER — Docker Daemon, Container State & Port Mapping
LAYER 5: SERVICE / TUNNEL — systemd, Nginx, cloudflared daemon status
LAYER 4: PORT & FIREWALL — ss, netstat, ufw, iptables, local listeners
LAYER 3: DNS & ROUTING — nslookup, dig, ip route, domain mapping
LAYER 2: NETWORK — IP Address, Wi-Fi/Ethernet link, ping local gateway
LAYER 1: POWER / HARDWARE — Raspberry Pi Power LED, SD Card, Cable

💡 Selalu troubleshoot dari bawah (Layer 1) ke atas (Layer 8)!

06 // Hardware & OS Baseline

Soalan Pertama: "Server Hidup Ke Tidak?"

1. Uptime Check
uptime

Memeriksa sama ada server baru shaja reboot atau terpadam secara tidak sengaja.

2. Memory Check
free -h

Memeriksa RAM yang tinggal dan sama ada Swap sedang digunakan secara berat.

3. Storage Check
df -h

Memastikan mount disk utama (seperti /) tidak mencapai status 100% penuh.

⚠️ "Jangan troubleshoot application kalau server OS itu sendiri tidak dapat hidup atau tidak boleh di-SSH!"
07 // Network Layer Diagnosis

Network Check Command

ip addr

Menyenaraikan semua network interface (eth0, wlan0, docker0) serta status IP address.

inet 192.168.1.50/24 brd 192.168.1.255 scope global eth0
ip route

Memeriksa routing table dan memastikan default gateway (router IP) dikonfigurasi dengan betul.

default via 192.168.1.1 dev eth0 proto dhcp src 192.168.1.50
hostname -I

Mendapatkan senarai ringkas IP address aktif tanpa output verbose.

192.168.1.50 172.17.0.1
08 // Basic Reachability Test

Ujian Ping (ICMP Probe)

Test 1: Local Gateway
ping 192.168.1.1

Menguji sambungan kabel/Wi-Fi dari server ke Router tempatan.

Test 2: Target Local Server
ping 192.168.1.50

Menguji jawapan daripada IP Raspberry Pi / Home Server anda.

Test 3: Internal Hostname
ping raspi.local

Menguji mDNS / Local resolution dalam LAN tempatan.

PENTING: Ping Failure Tidak Semestinya Sever Down!

Sesetengah Firewall atau Cloud Provider menyekat paket ICMP (Ping) atas sebab keselamatan. Server boleh jadi bertindak balas dengan sempurna pada port HTTP (80/443) walaupun ujian ping gagal atau timed out.

09 // Outbound Reachability

Memeriksa Sambungan Internet

Step 1: Test Direct IP Reachability
ping 1.1.1.1

✅ Jika BERJAYA:

• Physical Network OK
• Gateway Routing OK
• Outbound Internet OK

❌ Jika GAGAL:

• Masalah kabel/router ISP
• Default gateway route hilang

Step 2: Test Domain Resolution
ping cloudflare.com

✅ Jika 1.1.1.1 OK tetapi domain GAGAL:

• Sah! Ini adalah masalah DNS Resolver di server/router anda (cth: /etc/resolv.conf salah).

10 // DNS Layer Probe

DNS Troubleshooting Tools

Soalan utama yang perlu dijawab: "Adakah domain resolve ke destinasi IP / hostname yang betul?"

nslookup
nslookup app.domainbos.com

Perkakasan diagnostik asas yang disokong secara lalai pada Windows, Linux, dan macOS untuk menyemak balasan A record atau CNAME.

dig
dig app.domainbos.com +short

Alat Linux berkuasa tinggi yang memberikan maklumat terperinci seperti TTL (Time To Live), CNAME target, dan authoritative nameservers.

11 // Visual DNS Path

Aliran Resolusi DNS

Browser Client
DNS Resolver (1.1.1.1)
Cloudflare DNS Record
Target IP / CNAME

❌ Apabila Rekod DNS Salah/Stale:

Browser menghantar request ke IP lama atau IP acak. Server sebenar anda tidak pernah menerima sebarang trafik langsung!

12 // Skop Capaian

Private IP vs Public Access

1. Local / Private LAN
http://192.168.1.50:8080
  • Hanya boleh diakses dari dalam rumah / Wi-Fi yang sama.
  • Bypass seluruh infrastruktur Cloudflare, DNS awam & Tunnel.
  • Guna ini untuk mengesahkan app hidup!
2. Public Tunnel / Domain
https://app.domainbos.com
  • Boleh diakses dari seluruh dunia melalui internet.
  • Melibatkan DNS, Cloudflare Edge, SSL Certificate, dan Tunnel Agent.
  • Mempunyai banyak lapisan kebergantungan.
⚠️ "Jangan troubleshoot public layer sebelum local service disahkan berjalan dengan betul."
13 // Peraturan Pengasingan

Uji Localhost Terlebih Dahulu

Langkah Ujian Pertama Pada Server:
curl http://localhost:8080
Jika Ujian Ini Gagal (Connection Refused / Timeout): Punca pasti pada aplikasi local anda. Docker container crash, service terhenti, atau port terikat pada IP lain.
Jika Ujian Ini Berjaya (Return HTML / JSON): Aplikasi anda sihat! Masalah berada pada lapisan seterusnya (LAN IP binding, UFW firewall, atau Tunnel).
14 // Langkah Hirarki

Ujian Mengikut Hirarki (Layer Elevation)

1 localhost → curl http://127.0.0.1:8080
2 LAN / Private IP → curl http://192.168.1.50:8080
3 Cloudflare Tunnel → cloudflared status & connector logs
4 Domain & HTTPS → https://app.domainbos.com

"Naik SATU layer pada satu masa. Jika localhost sudah gagal, jangan menyalahkan Cloudflare."

15 // Port Diagnosis

Port Troubleshooting (ss command)

Command Utama Port Listening:
sudo ss -tulpn | grep 8080
0.0.0.0:8080

Aplikasi mendengar (listen) pada SEMUA IPv4 Interfaces. Boleh diakses dari localhost & peranti lain dalam LAN.

127.0.0.1:8080

Aplikasi mendengar LOCALHOST SAHAJA. Peranti LAN lain akan mendapat Connection Refused jika cuba akses via IP 192.168.x.x.

16 // Docker Port Mapping

Kesilapan Port & Mapping Docker

Contoh Command Docker Run:
docker run -d -p 8080:5000 my-python-app
HOST PORT 8080
CONTAINER PORT 5000
Kesilapan Biasa User: Cuba membuka http://192.168.1.50:5000 dari browser luar. Yang sepatutnya dibuka ialah port 8080 (Host port)!
17 // Sekatan Network

Firewall Troubleshooting

Linux (UFW Firewall)
sudo ufw status verbose

Jika port tidak dibenarkan:

sudo ufw allow 8080/tcp
Windows Server / Host Firewall

• Semak Windows Defender Firewall Inbound Rules.

• Pastikan Port 8080/443 tidak disekat oleh profil Public/Private network.

💡 Firewall hanyalah salah satu kemungkinan. Sekiranya localhost berfungsi tetapi LAN gagal, semak UFW!

18 // Linux Service Management

Systemd Service Diagnosis

Semak Status Service (systemctl)
sudo systemctl status nginx
🟢 Active: active (running) — Service berjalan sempurna.
🔴 Active: failed (result: exit-code) — Service crash atau ada error config.
systemctl status journalctl logs check config file restart service
19 // Log Systemd

Menganalisis Log (journalctl)

50 Line Log Terakhir
sudo journalctl -u nginx -n 50 --no-pager

Melihat mesej ralat terkini secara terus tanpa membuka fail log besar.

Follow Log Real-Time (-f)
sudo journalctl -u docker -f

Memantau log semasa anda membuat pencetus request di browser.

"Log memberitahu apa yang service cuba buat dan KENAPA ia gagal secara tepat."
20 // Application Layer

Troubleshooting Python Server

Checklist Diagnostik Python Web Server:

1. Adakah proses python3 hidup?
2. Adakah port (8080/5000) listening?
3. Adakah host terikat pada 0.0.0.0?
4. Adakah requirements.txt lengkap?
Uji secara manual di terminal untuk melihat traceback:
python3 app.py
21 // Swiss Army Knife Tool

curl — Alat Diagnosis Yang Sangat Berguna

Check Response Output
curl http://localhost:8080

Mendapatkan body tindak balas (HTML/JSON) langsung dari server.

Check HTTP Headers (-I)
curl -I http://localhost:8080

Melihat Status Code, Content-Type, dan Server Header sahaja.

curl membantu membezakan sama ada masalah berpunca daripada Browser Cache/Cookies atau Server/Application sebenar.
22 // Diagnostic Clues

HTTP Status Codes Cheat Sheet

200 OK
Request berjaya. Server menjawab dengan baik.
301 / 302
Redirect ke URL baru.
400 Bad Request
Syntax request client tidak difahami server.
401 / 403
Unauthorized / Forbidden (Gagal Auth / Permission).
404 Not Found
Server hidup, tetapi laluan (route/file) tak wujud.
500 Internal Error
Aplikasi crash atau ada bug dalam kod.
502 Bad Gateway
Proxy/Tunnel tak dapat hubungi upstream app.
503 Unavailable
Server terlalu sibuk atau sedang maintenance.
504 Gateway Timeout
Upstream app mengambil masa terlalu lama.

"HTTP status code ialah CLUE utama, bukannya penamat siasatan."

23 // Perbandingan Ralat

Perbezaan Kritik: 404 vs 500

404 NOT FOUND

Maksud: Server web (Nginx/Flask) berfungsi dengan sempurna dan menerima HTTP request, tetapi fail atau path URL (cth: /login.html) tidak wujud.

📍 Fokus: Semak URL path, routing file, atau static directory.
500 INTERNAL ERROR

Maksud: Request berjaya sampai ke aplikasi, tetapi kod aplikasi terhempas (crash/unhandled exception) semasa memproses data.

📍 Fokus: Semak log traceback aplikasi (app log / stdout).
24 // Container Diagnosis

Docker Troubleshooting Baseline

Container Running Sahaja
docker ps

Menunjukkan container yang SEDANG BERJALAN sahaja.

Semua Container (-a)
docker ps -a

PENTING! Menunjukkan container yang terhenti (Exited) berserta Exit Code.

💡 Sekiranya container menunjukkan status Exited (137), ini menandakan container dibunuh oleh Linux kerana kehabisan RAM (Out Of Memory)!
25 // Container Output

Docker Logs Inspection

Membaca Log Container:
docker logs --tail 100 <CONTAINER_NAME>
Aliran Diagnostik Apabila Container Crash:
1. docker ps -a → Cari nama/ID container yang Exited.
2. docker logs <container> → Baca mesej ralat Python / Node / DB.
3. Fix file config / kod → Rebuild / Restart container.
26 // Inside Container

Docker Exec (Internal Inspection)

Masuk Ke Dalam Container Active:
docker exec -it <CONTAINER_NAME> sh

Gunakan command ini untuk menyemak persekitaran dalaman container seperti lokasi fail, permission, atau ujian sambungan localhost di dalam container.

⚠️ AMARAN PENTING: Gunakan docker exec hanya untuk tujuan troubleshooting sahaja! Jangan mengubah suai kod atau fail di dalam container secara manual tanpa mengemas kini Dockerfile / Volume. Perubahan akan hilang apabila container di-restart!
27 // Pengasingan Isu

Masalah Host vs Container

HIERARKI STRUKTUR:
🖥️ HOST SERVER (Ubuntu / Raspberry Pi OS)
└── 🐳 Docker Engine
└── 📦 Container (App Web)
Masalah Peringkat Host:

• Host storage 100% penuh.
• Host kehabisan RAM/CPU.
• UFW Firewall menyekat port host.

Masalah Peringkat Container:

• Kod aplikasi Python ada error.
• Environment variable .env hilang.
• Port binding terikat pada 127.0.0.1 dalam container.

28 // Rangkaian Container

Aliran Docker Networking

🌐 Client Browser
🖥️ Host Port (:8080)
🐳 Docker Bridge
📦 Container Port (:8080)
Point Ralat Terpenting: Jika aplikasi Python di dalam container di-bind ke 127.0.0.1 (bukan 0.0.0.0), Docker Bridge tidak akan dapat meneruskan trafik dari Host Port ke Container!
29 // Reverse Proxy & Tunnel

Cloudflare Tunnel Troubleshooting

Aliran Sambungan Tunnel:
Browser Cloudflare Edge Tunnel Daemon Local Service
Soalan Siasatan: "Layer mana yang terputus?"
• DNS tak resolve? → Masalah Cloudflare DNS.
• 502 Bad Gateway? → Tunnel tak dapat bercakap dengan Local Service.
• Tunnel Down? → Service cloudflared di server mati.

🟡

🔴

31 // Daemon Diagnostics

Membaca Log Cloudflared

Semak Status Service Cloudflared:
sudo journalctl -u cloudflared -n 50 --no-pager
ℹ️ Nota: Nama service mungkin berbeza mengikut kaedah pemasangan (cth: cloudflared.service atau sistem container). Gunakan systemctl list-units | grep cloudflare jika nama tidak ditemui.
32 // Prinsip Pengesahan Origin

Validate Origin Before Edge

"Sahkan Servis Tempatan Dahulu Sebelum Menyalahkan Tunnel"

1 Jalankan curl http://localhost:8080 di server.
❌ Jika GAGAL → Stop! Selesaikan masalah local service dahulu. Jangan sentuh Tunnel.
✅ Jika BERJAYA → Local service OK. Sekarang teruskan troubleshoot Tunnel / Public Hostname.
33 // SSL / TLS Layers

HTTPS & SSL Troubleshooting

Checklist Diagnosis Sambungan HTTPS Gagal:
1. DNS Resolution → Adakah domain menghala ke Cloudflare / IP betul?
2. Cloudflare SSL Mode → Adakah ia ditetapkan ke Flexible / Full / Full (Strict)?
3. Tunnel Hostname Route → Adakah public hostname dipetakan ke URL local yang betul?
4. Certificate Match → Adakah nama domain sepadan dengan sijil TLS?
34 // Sijil Keselamatan

TLS / Certificate Warnings

Symptom Biasa:
  • Browser tunjuk: "Your connection is not private".
  • SSL_ERROR_BAD_CERT_DOMAIN.
  • Expired Certificate error.
Kemungkinan Punca Sebenar:
  • Domain name mismatch (akses via IP direct tetapi guna HTTPS).
  • Self-signed certificate tidak di-trust oleh browser.
  • Tarikah / Jam sistem Raspberry Pi terkeluar dari senarai (Clock drift).

"Jangan anggap semua TLS error datang dari certificate rosak. Semak jam server & DNS hostname!"

35 // Storage & Data Layer

Database Troubleshooting

✅ App Active
❌ DB Connection Refused
1. DB Service Running?
2. Correct Hostname/IP?
3. Port (5432/3306) open?
4. User/Pass correct?
36 // Konfigurasi Aplikasi

Environment Variables (.env) Errors

Contoh Mesej .env Yang Selamat (Placeholder):
DATABASE_HOST=<DATABASE_HOST_IP>
DATABASE_PORT=5432
DATABASE_USER=<USERNAME>
DATABASE_PASSWORD=<PASSWORD>

Kesilapan Biasa:

• Ejaan typo pada kunci nama variable (cth: DB_PASS vs DATABASE_PASSWORD).

• Fail .env tidak dimuatkan ke dalam container (tertinggal dalam docker-compose.yml).

37 // Storan Tepu

Disk Full Troubleshooting

Semak Ruang Storan Disk:
df -h /

Kesan Apabila Disk 100% Full:

• Database tidak dapat menulis transaksi data baru & terhempas (crash).

• Log systemd gagal ditulis.

• Docker container gagal dinyalakan.

🧹 Pembersihan Selamat: docker system prune -f atau bersihkan log purba di /var/log.
38 // Sumber Memori

Memory (RAM) Issues & OOM

Semak Memori (free -h)
free -h

Memeriksa jumlah RAM percuma, cached, dan Swap usage.

Pemantauan Proses Interactive
htop

Menyusun proses mengikut penggunaan peratusan RAM tertinggi.

ℹ️ Usage RAM tinggi tidak semestinya bermaksud bug! Linux menggunakan RAM lebihan untuk buffer cache bagi mempercepatkan sistem IO.
39 // Prestasi Pemprosesan

CPU Spike & Load Average

Semak Penggunaan CPU & Load:
top
Proses Mana? Adakah ia proses Python, Docker, atau build process?
Adakah Workload Berat? Adakah server sedang memproses kompresi video / data besar?
Adakah Stuck Loop? Adakah terdapat infinite loop dalam kod aplikasi?
40 // Kelajuan Sambungan

Network Latency & Packet Loss

Punca Server Terlalu Lambat:
  • High Wi-Fi latency / packet loss pada Raspberry Pi.
  • DNS Resolver mengambil masa lama untuk resolve hostname database.
  • Database query lambat kerana kekurangan Index.

"Ping bagus (rendah) TIDAK bermaksud aplikasi web pasti laju!"

41 // Senario Kajian Kes

Kajian Kes: "Website Lambat!"

❌ Tindakan Panik (JANGAN):

• Terus upgrade CPU/RAM server.

• Restart server tanpa menyemak log.

✅ Tindakan Sistemis (BUAT):

1. Check Network (ping / latency)

2. Check CPU & RAM (top / free -h)

3. Check Disk I/O (df -h)

4. Check Application & DB Query Logs

44 // Practical Lab Case 1

Scenario 1: Domain Tak Boleh Buka

Gejala: Browser menunjuk mesej ralat apabila membuka https://app.domainbos.com.
1. nslookup app.domainbos.com → Sahkan DNS resolve IP/CNAME.
2. Semak Cloudflare Dashboard → Adakah Tunnel Healthy?
3. curl http://localhost:8080 di server → Adakah app origin menjawab?
45 // Practical Lab Case 2

Scenario 2: 502 Bad Gateway

Penerangan 502: Gateway/Tunnel gagal berkomunikasi dengan aplikasi upstream tempatan.
1. docker ps → Adakah container target hidup?
2. ss -tulpn | grep 8080 → Adakah host listening pada port betul?
3. Semak config Cloudflare Tunnel → Adakah port origin dipetakan tepat (cth: 8080)?
46 // Practical Lab Case 3

Scenario 3: Application Error 500

Gejala: Browser memaparkan 500 Internal Server Error.
1. Semak log aplikasi: docker logs <container>
2. Cari Python Stack Trace (cth: KeyError, DatabaseConnectionError).
3. Semak fail .env & kebenaran akses database.
47 // Practical Lab Case 4

Scenario 4: Server Tiba-Tiba Perlahan

Gejala: Response time mengambil masa lebih 10 saat.
1. top / htop (Semak CPU)
2. free -h (Semak RAM)
3. df -h (Semak Disk Full)
4. docker stats (Semak container resource)
48 // Practical Lab Case 5

Scenario 5: Selepas Reboot Website Mati

Punca Biasa: Auto-restart policy tidak dikonfigurasi pada systemd / Docker!
1. Semak Docker restart policy: docker run --restart unless-stopped
2. Semak systemd service status: sudo systemctl enable cloudflared

53 // Dokumentasi Insiden

Dokumentasi Troubleshooting

Problem: Website memaparkan 502 Bad Gateway.
Cause: Docker container terhenti kerana kehabisan RAM.
Fix: Container di-restart & memory limit dinaikkan.
Verification: curl mengembalikan status 200 OK.
Prevention: Tambah Docker container auto-restart policy.
