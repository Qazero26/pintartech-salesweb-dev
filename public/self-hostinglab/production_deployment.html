01. Apa Itu Production?

Memahami jurang antara kawasan ujikaji tempatan dan alam realiti pengguna.

DEVELOPMENT

Tempat Membina & Menguji

Environment khas untuk pembangun (developer) membuat eksperimen, menambah feature, dan mencari bugs tanpa mengganggu sesiapa.

Developer → Code → Test
PRODUCTION

Digunakan Pengguna Sebenar

Environment awam yang mengendalikan transaksi sebenar, data kritikal, dan pengguna sebenar. Toleransi terhadap kegagalan adalah sangat rendah.

Users → Internet → System → Real Data

"Working" vs "Production Ready"

Aplikasi yang boleh dibuka tidak bermaksud ia bersedia untuk bebanan sebenar.

WORKING SETUP
  • Website boleh dibuka di browser
  • (Tetapi tiada perlindungan jika crashed, tiada backup jika hard disk rosak)
PRODUCTION-READY SETUP
✓ Authentication
✓ Security Layer
✓ Monitoring
✓ Centralized Logging
✓ Automated Backup
✓ Tested Recovery
✓ Zero-Downtime Updates
✓ Secrets Management
"Berjaya berjalan ≠ Production Ready."

Perbandingan Development vs Production

Perbezaan keperluan operasi mengikut persekitaran.

Komponen Development Production
Infrastruktur Laptop / PC Tempatan Server Dedikasi / VPS / Cloud
Konfigurasi Debug mode = ON Production Config (Hardened)
Database Local DB / SQLite / Mock Real DB + Replicated Storage
Sambungan Temporary Tunnel / Localhost Stable Domain + Strict HTTPS
Data Test / Dummy Data Data Pengguna Sebenar (Sensitif)
Pemulihan Restart Manual Auto-Recovery + Auto-Restart

02. Domain: Identiti Stabil

Menghubungkan pengguna ke server melalui nama yang mudah diingati.

Contoh Production Domain
app.domainbos.com
1. User

Taip URL dalam browser

2. DNS Lookup

Tukar nama domain ke IP Cloudflare

3. Application

Trafik sampai ke aplikasi sasaran

Domain memberikan stable public identity. Jika IP server fizikal bertukar, pengguna tetap membuka URL yang sama tanpa sebarang gangguan.

03. HTTPS & Keselamatan Sambungan

Enkripsi lalu lintas data menggunakan TLS/SSL.

http://example.com ❌ Tidak Selamat
https://example.com ✅ Selamat (TLS)

3 Teras Utama HTTPS (TLS Goals):

🔒 Encryption

Orang tengah tidak boleh membaca kandungan paket data.

🛡️ Authentication

Memastikan anda berhubung dengan server sebenar, bukan penyamar.

✨ Integrity

Memastikan data tidak diubah suai semasa dalam perjalanan.

⚠️ Peringatan Penting: "HTTPS tidak menjadikan application anda automatik secure daripada SQL Injection atau bug koding!"

04. Reverse Proxy

Penjaga pintu hadapan (gatekeeper) server anda.

Internet
→ HTTPS:443 →
Reverse Proxy
→ HTTP:8080 →
Application Container

Fungsi Utama Reverse Proxy:

  • • TLS Termination: Menguruskan sijil SSL/TLS di satu tempat sahaja.
  • • Request Routing: Mengarahkan domain berbeza ke aplikasi berbeza.
  • • Security Shielding: Menyembunyikan port sebenar aplikasi tempatan.
  • • Centralized Header Control: Menguruskan CORS, Gzip compression, dan Security Headers.

Menguruskan Pelbagai Subdomain

Satu Reverse Proxy mengendalikan banyak servis serentak.

DOMAIN UTAMA: domainbos.com
app.domainbos.com
↓
Web App (Frontend)
api.domainbos.com
↓
REST API Backend
admin.domainbos.com
↓
Admin Dashboard

Reverse proxy membaca Host Header daripada HTTP Request dan menyalurkan trafik ke port tempatan yang betul (contoh: 3000, 8080, 9000).

05. Containerization (Docker)

Membungkus aplikasi berserta dependency ke dalam kontena yang konsisten.

STRUKTUR SERVER DOCKER:
Linux OS (Host Machine)
Docker Engine
Web Container
API Container
Worker Container
Database Container
✅ Consistent Environment: "It works on my machine" tidak lagi menjadi alasan.
✅ Isolation: Masalah pada Web App tidak merosakkan Database secara langsung.

Docker Compose: Multi-Container Setup

Menguruskan keseluruhan stack aplikasi dalam satu fail deklaratif.

# docker-compose.yml
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
  api:
    build: ./api
    environment:
      - DATABASE_HOST=db
  db:
    image: postgres:15-alpine
    volumes:
      - db_data:/var/lib/postgresql/data

Docker Compose membantu mendefinisikan network tempatan, volume storan, dan hubungan kebergantungan (dependencies) antara servis hanya dengan satu perintah: docker compose up -d.

06. Environment Variables (.env)

Asingkan konfigurasi aplikasi daripada kod sumber (source code).

# Contoh fail .env dalam Production
APP_ENV=production
APP_PORT=8080
DATABASE_HOST=db
LOG_LEVEL=warn
Mengapa Penting? Kod aplikasi yang sama boleh dijalankan di laptop (development) atau di server (production) tanpa perlu mengubah walau satu baris kod sumber—hanya tukar nilai Environment Variable.

07. Secrets Management

Melindungi maklumat rahsia daripada kebocoran.

❌ JANGAN SIMPAN:

  • • API Keys & Tokens
  • • Database Passwords

  • • SSH Private Keys

Dalam: Git Repository, Frontend JS, atau Public Code.

✅ GUNAKAN:

  • • Production Environment Variables

08. Database Deployment & Isolation

Database adalah jantung sistem. Ia tidak sepatutnya terdedah kepada awam.

ISOLASI NETWORK DATABASE
Public Internet → Application Server → Database (Internal Network Only)

🔒 Prinsip Utama: Database TIDAK PERLU exposed ke public internet (Jangan buka Port 5432 / 3306 pada IP awam).

🛡️ Hanya container aplikasi dalam Docker Network dalaman yang dibenarkan berkomunikasi dengan Database.

09. Persistent Storage & Volume

Memastikan data tidak hilang apabila kontena dipadam atau di-update.

CONTAINERS

Boleh dipadam, diganti, atau di-restart pada bila-bila masa (Stateless / Ephemeral).

DATA / VOLUMES

Mesti kekal tersimpan secara selamat di dalam storan fizikal host server (Stateful).

Container → Docker Volume → Host Storage
"Container boleh hilang. Data tidak sepatutnya hilang."

10. Logging

"Kalau ada masalah, kita perlu tahu apa yang berlaku."

• Application Logs: Exception, stack traces, logic errors.
• Access Logs: HTTP status codes (200, 404, 500), IP, latency.
• Auth Logs: Percubaan login gagal, perubahan password.
• System Logs: Service restarts, OOM (Out Of Memory) killed events.
⚠️ Peraturan Utama Log: JANGAN sesekali meletakkan maklumat sensitif (password, credit card, JWT token) dalam fail log!

12. Health Checks

Menjawab soalan penting: "Adakah aplikasi ini benar-benar sihat?"

Readiness Probe

Memastikan aplikasi bersedia menerima trafik (cth: sambungan DB sudah sedia).

15. Backup Strategy

Insurans terpenting untuk data produksi anda.

Application Data → Database Dump → Encrypted Backup File → Remote Storage (Cloud S3 / Offsite)
Regular (Berkala)
Protected (Enkripsi)
Monitored (Dipantau)
Tested (Diuji)

Prinsip 3-2-1 Backup Rule

Panduan standard industri untuk keselamatan salinan data.

3
Salinan Data

1 Data Asal + 2 Salinan Backup

2
Jenis Media Berbeza

Contoh: Local NVMe SSD + External NAS

1
Lokasi Offsite

Disimpan di luar bangunan (Cloud / Remote Server)

Sesuaikan strategi backup ini mengikut tahap toleransi risiko dan bajet anda.

16. Disaster Restore Testing

Ujian pemulihan data adalah lebih kritikal daripada proses membuat backup.

Backup File → Restore Procedure → Integrity Verification → Application OK
"Backup yang belum diuji bukan bukti recovery."

Lakukan ujian restore secara berkala (cth: sebulan sekali) dalam environment ujian untuk memastikan fail backup tidak rosak (corrupted).

18. Deployment Strategies

Teknik kemaskini versi aplikasi di persekitaran produksi.

1. Manual Deployment

Tutup app lama, ganti kod, buka app baru. Memerlukan downtime seketika.

2. Rolling Deployment

Kemaskini kontena satu per satu tanpa menutup keseluruhan servis.

3. Blue/Green Deployment

Dua persekitaran identikal berjalan serentak. Trafik alih serta-merta.

4. Canary Deployment

Lepaskan versi baru kepada sebilangan kecil peratusan pengguna dahulu.

Blue / Green Deployment

Strategi penukaran trafik sepantas kilat.

BLUE (Active - Version 1.0)

Menerima 100% Trafik Pengguna

GREEN (Idle - Version 2.0)

Diuji Sepenuhnya & Sedia Digunakan

Setelah sedia, Reverse Proxy ditukar haluan untuk mengarah pengguna ke persekitaran GREEN. Jika ada isu, alih semula trafik ke BLUE dalam beberapa saat.

Canary Deployment

Mengurangkan risiko dengan pengeluaran secara berperingkat.

Fasa 1: Pengeluaran Awal 95% Old | 5% New Traffic
Fasa 2: Pemantauan Stabil 80% Old | 20% New Traffic
Fasa 3: Pengeluaran Penuh 0% Old | 100% New Traffic

Mengesan bug tersembunyi dengan menguji pada kelompok pengguna kecil sebelum mengemas kini keseluruhan pelayan.

19. Rollback Plan

Jalan keluar cemas apabila deployment baru mengalami kegagalan.

Deploy v2.0 → Critical Bug Detected → Trigger Rollback → Restore Stable v1.0
"Setiap deployment strategy mesti ada jalan keluar (Exit Plan)."

Database Migration Strategy

Menguruskan perubahan skema database tanpa merosakkan data sedia ada.

1. Backup DB → 2. Run Migration → 3. Deploy App → 4. Verify Integrity
⚠️ PENTING: Jangan ubah skema database produksi secara manual melalui SQL command GUI tanpa fail skrip migration dan pelan pemulihan!

20. Konsep Zero-Downtime Deployment

Menukar versi aplikasi tanpa memutuskan pengguna yang sedang aktif.

Bagaimana Ia Berfungsi?

Reverse Proxy menahan trafik baharu seketika, mengarahkan sambungan ke kontena baru yang telah disahkan sihat (Health Check OK), sebelum menamatkan kontena lama.

Teknologi Terlibat

• Reverse Proxy Graceful Reload
• Docker Swarm / Kubernetes
• Load Balancer Session Draining

Raspberry Pi vs VPS

Memilih infrastruktur fizikal yang tepat untuk jenis beban kerja.

🍓 Raspberry Pi (Home Server)
  • ✓ Sangat rendah penggunaan elektrik
  • ✓ Kawalan fizikal 100% di rumah
  • ✓ Cemerlang untuk persekitaran pembelajaran
  • ⚠️ Kebergantungan kepada talian internet rumah & bekalan elektrik tempatan
☁️ VPS (Cloud Server)
  • ✓ Sambungan internet & bekalan kuasa gred Datacenter
  • ✓ Public IP statik yang stabil
  • ✓ Mudah ditambah spesifikasi (Flexible Scaling)
  • ⚠️ Memerlukan yuran komitmen bulanan

Home Production Deployment

Production tidak semestinya bermaksud Cloud bernilai ribuan ringgit.

Home Production bermaksud:
Home Server (Raspberry Pi / Mini PC) + Pengguna Sebenar + Data Sebenar + Keperluan Uptime Sebenar.

Meskipun bertempat di rumah, anda masih perlu menerapkan amalan keselamatan, backup, dan monitoring yang ketat!

23. Disaster Recovery Scenario

Bersedia menghadapi senario terburuk.

⚡ Power Outage
💾 Storage Disk Failure
🔥 Database Corruption
🔓 Credential Compromise
DETECT → CONTAIN → RECOVER → VERIFY → RESTORE SERVICE

Objektif Pemulihan: RPO & RTO

Dua parameter kritikal dalam merancang pemulihan bencana.

RPO (Recovery Point Objective)

Berapa banyak data yang sanggup anda rugi (hilang)?

Contoh: RPO = 1 Jam (Kekerapan Backup)

RTO (Recovery Time Objective)

Berapa lama sistem boleh berada dalam keadaan terhenti (down)?

Contoh: RTO = 4 Jam (Masa Pemulihan)
