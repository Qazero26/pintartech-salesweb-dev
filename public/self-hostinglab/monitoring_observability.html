Monitoring vs Observability

Dua Konsep Penting Yang Selalu Disalah TAFSIR

MONITORING

"Adakah sistem sihat?"

Fokus kepada mengumpul dan memaparkan data yang sudah diketahui (known-knowns). Mengesan kegagalan secara luaran.

• CPU > 90% (Alert triggered)
• Disk space > 95%
• Website status: HTTP 500
OBSERVABILITY

"Mengapa sistem berkelakuan begini?"

Kemampuan infer keadaan dalaman sistem berdasarkan data telemetry output (unknown-unknowns).

Metrics + Logs + Traces + Context
➔ Memahami *kenapa* query spesifik menyebabkan memory leak sewaktu user checkout.
💡 Monitoring memberitahu anda bahawa sistem rosak. Observability membantu anda memahami punca utama (*why & how*).

Tiga Pilar Observability (MELT)

Teras telemetry bagi sistem moden

📊

1. METRICS

Numerical measurements secara agregat mengikut sela masa.

Soalan: "Apa yang berlaku?"
Contoh: CPU %, Request Count, Latency 150ms.
📝

2. LOGS

Rekod teks peristiwa bercap masa (timestamped events).

Soalan: "Apa yang dicatat/terjadi?"
Contoh: ERROR: Connection refused to DB.
🔍

3. TRACES

Perjalanan satu request melintasi pelbagai mikro-perkhidmatan.

Soalan: "Di mana request lambat?"
Contoh: API (5ms) ➔ DB (2.4s) ➔ Cache (2ms).

Jenis Metric Utama: Counter vs Gauge

Dua sifat asas pergerakan nombor dalam Prometheus

1. COUNTER (Tergumpal Naik)

Monotonically Increasing

Nilai nombor yang hanya boleh naik atau reset ke 0 bila server restart. Tidak pernah berkurang secara biasa.

• Jumlah HTTP requests: http_requests_total = 452,091
• Jumlah Ralat Sistem: errors_total = 142
• Total Bytes Transmitted: net_bytes_sent = 8.4GB
📌 Kegunaan: Dikira kadar persaat menggunakan fungsi rate() dalam PromQL.

2. GAUGE (Naik & Turun)

Flexible Value

Nilai semasa snapshot yang boleh naik dan turun pada bila-bila masa mengikut keadaan semasa.

• CPU Utilization: node_cpu_seconds = 45.2%
• RAM Usage: memory_used_bytes = 4.1GB
• Suhu Raspberry Pi: cpu_temperature_c = 52°C
📌 Kegunaan: Mengukur baki, peratusan, dan status semasa sistem.

Latency (Kelewatan Respons)

"Berapa lama sesuatu request mengambil masa untuk diproses?"

SENARIO MASA RESPONS Client ➔ Server ➔ Response
50 ms
⚡ Super Fast
120 ms
✅ Normal / Good
800 ms
⚠️ Slow / Laggy
5.0 sec
❌ Unacceptable
Troubleshooting Insight: Latency tinggi selalunya berpunca daripada unindexed DB queries, external API block, atau resource contention (CPU/RAM limit).

Throughput (Kadar Pemprosesan)

"Berapa banyak kerja boleh diproses dalam satu tempoh masa?"

Contoh Ukuran Throughput

Web Requests: 150 req/sec (RPS)
Network I/O: 10 MB/sec
DB Transactions: 45 TPS

Latency ≠ Throughput

Sistem boleh mempunyai **latency rendah** (50ms per request) tetapi **throughput terhad** jika hanya dapat proses 1 request pada satu masa (tiada concurrency).

Analog Lebuhraya:
• Latency = Kelajuan kereta (km/j)
• Throughput = Jumlah kereta lalu melepasi tol sesaat

Error Rate (Kadar Ralat)

Nisbah permintaan gagal berbanding jumlah keseluruhan request

FORMULA
Error Rate = ( Failed Requests / Total Requests ) × 100%
Contoh Pengiraan:
1,000 total requests received
10 failed HTTP 500 errors
➔ Error Rate = 1.0%

Kaitan Dengan Alerting

Lonjakan Error Rate tiba-tiba (cth: dari 0.1% ke 5%) adalah petanda terbaik berlakunya **regresi deployment** atau **downstream outage**.

Availability (Ketersediaan Perkhidmatan)

"Berapa peratusan masa perkhidmatan boleh berfungsi dan diakses?"

99% Availability
Downtime: ~3.65 hari / tahun

Sesuai untuk Homelab / Personal Project.

99.9% ("Three Nines")
Downtime: ~8.76 jam / tahun

Standard Perniagaan SME / Internal Apps.

99.99% ("Four Nines")
Downtime: ~52.6 minit / tahun

Sistem Perbankan / Enterprise Critical.

⚠️ Ingatan Pedagogi: Tidak semua sistem memerlukan 99.99%. Menambah "nine" meningkatkan kos infrastruktur dan kompleksiti secara eksponen!

Uptime vs Application Health

Mengapa status "Running" boleh menipu anda

Docker Container: RUNNING

Process ID (PID) masih wujud dalam OS. Sistem OS menganggap bekas Docker ini aktif.

$ docker ps
Status: Up 14 days (healthy)

Application: BROKEN

Aplikasi mengalami Deadlock atau terputus sambungan ke Database. HTTP request memulangkan 500 Internal Error.

HTTP GET /api/users
500 Internal Server Error (Database unreachable)
📢 PENTING: Process Running ≠ Application Healthy!

Health Checks (Liveness vs Readiness)

Mekanisme proaktif bertanya khabar perkhidmatan

1. Liveness Probe

"Adakah perkhidmatan ini masih hidup/wujud?"

Jika Gagal ➔ Orchestrator (Docker Swarm/K8s) akan KILL & RESTART container secara automatik.

2. Readiness Probe

"Adakah aplikasi sedia terima trafik pengguna?"

Jika Gagal ➔ Reverse Proxy akan STOP HANTAR TRAFIK ke container ini sehingga ia sedia (cth: habis loading cache).
Standard Endpoint Contoh: GET /healthz atau GET /ready ➔ Return HTTP 200 OK {"status": "UP"}

Heartbeat Mechanism

"I'm alive!" — Isyarat denyutan nadi berkala

Bagaimana Heartbeat Berfungsi?

  1. Server / Agent menghantar 'ping' berkala setiap 60 saat ke Central Monitor (cth: Uptime Kuma).
  2. Jika Central Monitor menerima isyarat ➔ Status 🟢 GREEN.
  3. Jika tiada isyarat diterima selama >3 minit ➔ 🚨 ALERT: Server/Tunnel Down!
HEARTBEAT FLOW
Server ➔ PING (10:00:00) ➔ OK
Server ➔ PING (10:01:00) ➔ OK
Server ➔ MISSED (10:02:00) ➔ 🚨 TRIGGER ALERT

Logs (Rekod Peristiwa Bercap Masa)

"Penceritaan Terperinci Peristiwa Sistem"

2026-08-18 10:21:01 [INFO] User auth_id=8923 login successfully from IP=203.0.113.10
2026-08-18 10:21:45 [WARN] High memory usage detected on worker thread #4
2026-08-18 10:22:14 [ERROR] Database connection failed: timeout after 5000ms
Kelebihan Log: Menyediakan konteks terperinci (siapa, bila, di mana) yang tidak ditunjukkan oleh angka metrics.
Cabaran Log: Isipadu data sangat besar. Memerlukan penapisan & log rotation yang betul.

Log Severity Levels

Tahap kepentingan log untuk kawalan kejelasan data

DEBUG

Maklumat teknikal terperinci untuk developer semasa pembangunan.

INFO

Operasi normal aplikasi (cth: User login, job completed).

WARNING

Isu potensi bermasalah tetapi sistem masih berjalan.

ERROR

Satu fungsi/operasi gagal diproses.

CRITICAL

Seluruh aplikasi crash atau tidak berfungsi langsung.

Structured Logging (Format JSON)

Membolehkan mesin & parser seperti Loki / Elasticsearch membuat query pantas

❌ Unstructured (Plain Text)
User login failed for user123 from IP 203.0.113.10 at 10:22

Sukar diproses oleh mesin. Perlu Regex kompleks.

✅ Structured (JSON Format)
{
  "timestamp": "2026-08-18T10:22:00Z",
  "level": "error",
  "event": "login_failed",
  "user_id": "user123",
  "ip_address": "203.0.113.10"
}

Sangat mudah dibuat carian: event=="login_failed"

🔒 KESELAMATAN: Jangan sesekali simpan Password, JWT Token, atau Card CVV dalam logs!

Log Correlation (Correlation ID)

Menghubungkan log merentas pelbagai perkhidmatan microservices

Request ID Generation: `X-Correlation-ID: req-abc-789`
[Reverse Proxy] Pass header ➔ req-abc-789
[App Service] Receive request ➔ Log entry tagged with req-abc-789
[DB Service] Execute query ➔ Log query tagged with req-abc-789

Dengan Correlation ID, anda boleh `grep req-abc-789` untuk melihat **keseluruh perjalanan transaksi** pengguna secara lengkap!

Pemantauan CPU & Load Average

"Tinggi CPU tidak sentiasa bermakna serangan siber!"

Metrik CPU Utama:

  • • CPU Utilization: Peratusan masa CPU aktif.
  • • Load Average: Purata giliran proses menunggu CPU. (Load > Jumlah Core = Sesak).
  • • CPU Temp: Suhu cip pemproses (Kritikal untuk Raspberry Pi).

Punca CPU Tinggi:

1. Heavy application processing (Video transcoding)
2. Unindexed Database Query (Full Table Scan)
3. Scheduled Backup Job (Cron Job Compression)
4. Runaway Process / Infinite Loop

RAM & Out-Of-Memory (OOM) Killer

Bahaya kehabisan memori fizikal pada Linux & Docker

Status Memori Linux

Nota: Linux menggunakan RAM kosong sebagai Buffers/Cache secara bijak!

Bahaya OOM Killer!

Apabila RAM fizikal + Swap habis, Linux Kernel dipaksa mematikan proses terbesar secara paksa:

Raspberry Pi Temperature & Throttling

Menjaga perkakas SBC (Single Board Computer) daripada terlampau panas

Thermal Throttling

Apabila suhu CPU Raspberry Pi mencapai >80°C, perkakas secara automatik menurunkkan kelajuan clock CPU untuk mengelakkan kerosakan fizikal.

Suhu Naik ➔ Performance Drops ➔ Server Slow!

Langkah Pencegahan

  • • Kipas penyejuk (Cooling Fan)

The Four Golden Signals (Google SRE)

Empat metrik paling utama untuk memantau mana-mana sistem perkhidmatan

1. LATENCY

Masa diambil untuk memproses permintaan (membezakan request berjaya vs gagal).

2. TRAFFIC

Ukuran permintaan terhadap sistem (cth: HTTP requests/sec, network I/O).

3. ERRORS

Kadar permintaan gagal (cth: HTTP 500, DB timeouts, exception errors).

4. SATURATION

Berapa penuh sumber sistem (CPU 90%, RAM 95%, DB Connection pool 99%).

Understanding Saturation

"Sejauh mana sistem menghampiri had maksimanya?"

AMARAN SATURASI TINGGI (RISK DEGRADATION):
CPU: 95% ➔ Queueing delay bermula
RAM: 92% ➔ Risk OOM Swap Thrashing
Disk: 98% ➔ Danger Write Failure
DB Conn Pool: 96/100 ➔ Client Connection Rejected

Alerting Fundamentals

Memberitahu Admin apabila perkhidmatan memerlukan perhatian

🚨 Tujuan Alert

Alert **bukan sekadar** laporan statistik. Alert hanya patut dihantar apabila **tindakan manusia (human action)** diperlukan secara serta-merta!

Siklus Alert:
1. Metric melepasi Threshold
2. Peringkat Pending (cth: berlanjutan 5 minit)
3. Alert Firing ➔ Hantar Notifikasi

Good Alert vs Bad Alert

Menghindari kebisingan tidak berguna

❌ BAD ALERT (Spam / Noise)

IF CPU > 80% THEN ALERT

Punca: CPU melonjak 81% selama 3 saat akibat cron job biasa, menghasilkan alert bising mengganggu tidur admin!

✅ GOOD ALERT (Actionable)

IF CPU > 90% AND Latency > 2s FOR 10 minutes THEN ALERT

Guna syarat berganda (multi-condition) dan tetingkap masa (time window) untuk mengesahkan masalah sebenar.

Alert Fatigue (Keletihan Alert)

Bahaya terbesar dalam pengurusan pemantauan

😵 Fenomena Alert Fatigue

Apabila sistem menghantar 100+ alert sehari yang tidak memerlukan tindakan (false alarms), Admin akan mula mengabaikan atau meletakkan notifikasi pada mod Mute.

Kesan: Apabila INSIDEN SEBENAR berlaku, tiada siapa yang menyedarinya kerana menyangka ia sekadar spam biasa!

SLI (Service Level Indicator)

Ukuran kuantitatif sebenar prestasi perkhidmatan

SLI = MEASUREMENT (APA YANG DIUKUR SEBENARNYA)
• Availability SLI: 99.95% daripada request berjaya (HTTP 200).
• Latency SLI: 95% daripada request selesai dalam masa < 200ms.
• Error Rate SLI: 0.05% ralat dicatat dalam tempoh 30 hari.

SLO (Service Level Objective)

Sasaran prestasi internal yang ditetapkan oleh pasukan perkhidmatan

SLO = TARGET / OBJECTIVE (MATLAMAT INTERNAL)
"Ketersediaan API web mestilah sekurang-kurangnya 99.9% setiap bulan."
Perbezaan: SLI ialah ukuran *sebenar*, SLO ialah *sasaran* yang hendak dicapai.

SLA (Service Level Agreement)

Perjanjian Kontrak Perniagaan dengan Pelanggan

SLA = CONTRACT / BUSINESS COMMITMENT

Komitmen undang-undang antara penyedia perkhidmatan dan pelanggan. Mengandungi **penalti kewangan** jika SLO gagal dipenuhi.

SLI (Ukuran Sebenar)
SLO (Sasaran Internal)
SLA (Kontrak + Penalti)

Percentiles (P50, P95, P99 Latency)

Mengapa nilai purata (Average) menyembunyikan masalah sebenar

❌ BAHAYA AVERAGE (MEAN)

9 request mengambil 100ms, tetapi 1 request mengambil 10,000ms (10 saat). Purata = 1,090ms!

Purata memberi tanggapan salah seolah-olah semua orang mengalami 1 saat lag.

✅ PERCENTILES (TAIL LATENCY)

• P50 (Median): 50% pengguna dapat < 100ms.
• P95: 95% pengguna dapat < 200ms.
• P99 (Tail): 1% pengguna paling malang mengalami 10s!

  severity: critical

  summary: "Disk space on {{ $labels.instance }} is above 90%"

Alert Rule: Website Down

Mengesan kegagalan perkhidmatan sepenuhnya

🚨 ALERT DEFINITION
IF probe_success == 0 FOR 2 minutes
THEN TRIGGER "Website Down Alert" ➔ TELEGRAM BOT

Alert Rule: High Error Rate

Mengesan lonjakan ralat aplikasi

⚠️ ALERT DEFINITION
IF (rate(http_requests_5xx[5m]) / rate(http_requests_total[5m])) > 0.05
FOR 5 minutes THEN TRIGGER "High Error Rate (>5%)"

Alert Rule: Database Pressure

Mengesan tekanan sambungan pangkalan data

🗄️ ALERT DEFINITION
IF pg_stat_activity_count > 90 OR pg_query_duration_seconds > 2s
THEN TRIGGER "Database Pressure Warning"

Alert Rule: Raspberry Pi Thermal

Mengesan suhu tinggi perkakas

🍓 ALERT DEFINITION
IF rpi_cpu_temperature > 75°C FOR 5m
THEN TRIGGER "High CPU Temperature Warning"

Kesilapan Lazim Monitoring

Kesilapan yang perlu dielakkan oleh Admin

❌ KESILAPAN LAZIM:
• Monitor terlalu banyak metrik tidak berguna
• Tiada retention policy (Log memenuhi disk)
• Terlalu banyak alert sehingga berlaku Alert Fatigue
• Hanya monitor perkakas, lupa monitor aplikasi!

Kesilapan Lazim Observability

Jebak kesilapan tahap observability

❌ KESILAPAN OBSERVABILITY:
• Simpan log tanpa Correlation ID
• Tiada request tracing untuk microservices
• Menyimpan log tanpa format Structured JSON
• Alert tidak dihubungkan dengan Runbook pembaikan

Runbooks (Panduan Pembaikan Alert)

Dokumentasi langkah pembaikan cepat apabila alert berbunyi

📖 RUNBOOK: DiskUsageAbove90Percent
  1. Semak penggunaan disk: df -h
  2. Cari direktori terbesar: du -sh /* | sort -h
  3. Bersihkan fail Docker tidak terpakai: docker system prune -a
  4. Semak log rotation status: logrotate -f /etc/logrotate.conf

MTTR (Mean Time To Recovery)

Purata Masa Pemulihan Perkhidmatan

MTTR = Purata Masa (Insiden Berlaku ➔ Service Pulih)

Tujuan Observability adalah untuk mengurangkan MTTR dari berjam-jam kepada minit sahaja!

MTBF (Mean Time Between Failures)

Purata Jarak Masa Antara Kegagalan

MTBF = Purata Masa Operasi Tanpa Gangguan

Semakin tinggi nilai MTBF, semakin stabil infrastruktur anda.

Konsep Error Budget

Toleransi kegagalan yang dibenarkan untuk inovasi

FORMULA ERROR BUDGET
Error Budget = 100% - SLO Target
Jika SLO = 99.9%, Error Budget = 0.1% downtime yang dibenarkan sebulan untuk deploy feature baharu.
