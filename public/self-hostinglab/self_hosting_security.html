Konsep Asas

Kenapa Security Penting?

Perbezaan persekitaran tertutup vs persekitaran terbuka

🏠 Localhost (Terpencil)
Internet ↓ ❌ (Terhalang) localhost (127.0.0.1)

Hanya laptop/PC anda sahaja yang boleh akses. Tiada ancaman luar kerana tiada sambungan terus dari Internet.

🌐 Didedahkan ke Internet
Internet ↓ 🌐 (Terbuka) Server (Public IP / Tunnel)

Mana-mana individu atau bot di seluruh dunia boleh menghantar request ke server anda. Attack surface menjadi jauh lebih besar!

"Online ≠ Secure."
Ancaman & Risiko

Apa Itu Attack Surface?

Semua bahagian sistem yang boleh menjadi titik risiko serangan

📌 Komponen Attack Surface
  • Open Ports: Port yang sedia menerima sambungan.
  • Web Applications: Kod app yang ada bug.
  • SSH: Akses pentadbiran remote.
  • APIs & Login Pages: Pintu masuk pengguna.
  • Admin Panels: Kawalan penuh sistem.
  • Dependencies: Library pihak ketiga yang lapuk.

Prinsip Keselamatan #1

Minimize Exposure

"Jangan expose benda yang tidak perlu."

❌ Amalan Berisiko (Amatur)
  • Expose Database (Port 3306 / 5432) ke Public.
  • Expose Admin Panel tanpa perlindungan khas.
  • Expose Development Server yang belum disiapkan.
✅ Amalan Lebih Baik (Defensive)
Internet → HTTPS/Access → Application → Internal Services

Hanya benarkan trafik melalui proxy/access layer. Pastikan database dan service dalaman kekal tertutup!

Rangkaian

Open Ports

Fahami fungsi dan risiko port yang dibuka

Port bukan secara automatik berbahaya. Tetap setiap exposed service perlu difahami dan diamankan.

Port 22
SSH (Secure Shell)
Digunakan untuk pengurusan remote server secara CLI.
Port 80 / 443
HTTP / HTTPS
Digunakan untuk lalu lintas laman web awam.
Port 8080
Dev / App Server
Port ujian seperti Python Flask, Node.js atau Docker.
📌 Ingat: "Open port bermaksud ada service yang sedang aktif menunggu sambungan."
Pemeriksaan Sistem

Port Scanning Secara Defensive

Memeriksa pendedahan sistem anda sendiri (Self-Audit)

🔍 Tujuan Audit Defensive

Seorang Administrator Security melakukan semakan pada server sendiri untuk soalan:

"Apakah service yang saya sendiri expose tanpa sedar?"

  • ✓ Asset Inventory: Tahu apa yang berjalan.
  • ✓ Verify Firewall: Pastikan rule berfungsi.
  • ✓ Verify Config: Tiada port terlepas.
  • ✓ Reduce Exposure: Tutup port lama.
⚠️ Etika & Undang-undang: Hanya imbas sistem sendiri atau lab yang diberikan kebenaran bertulis. Jangan imbas target luar tanpa kebenaran!
Kawalan Trafik

Firewall — Pintu Kawalan

Menapis trafik masuk dan keluar berdasarkan aturan

Internet ↓ 🔥 FIREWALL (Penapis) ↓ Server
🎯 Firewall Mengawal Trafik Berdasarkan:
  • Source: Dari mana IP asal?
  • Destination: Ke mana sasaran IP?
  • Port: Port berapa yang diminta?
  • Protocol: TCP, UDP, ICMP?
  • Direction: Masuk (Inbound) / Keluar (Outbound).
💬 Analogi: Firewall ialah pengawal pintu pagar (Guard House). Ia menentukan trafik mana yang dibenarkan masuk atau keluar.
Rangkaian

Inbound vs Outbound

Memahami arah aliran data dan hubungannya dengan Tunnel

📥 INBOUND TRAFFIC
Internet → Server

Trafik yang digesa dari luar masuk ke dalam server anda. Memerlukan open inbound port jika menggunakan Port Forwarding biasa.

📤 OUTBOUND TRAFFIC
Server → Internet

Trafik yang dimulakan oleh server anda ke luar (contoh: download software update atau membuat sambungan tunnel).

☁️ Kaitan Cloudflare Tunnel: Tunnel bermula dari server ke luar (Outbound connection). Oleh itu, anda TIDAK memerlukan Inbound Port Forwarding di router rumah!
Prinsip Keselamatan #2

Default Deny Policy

"Jika tidak diperlukan secara jelas, blokkan ia!"

🛡️ Pendekatan Default Deny (Strict)

Secara lalai, tutup SEMUA port. Hanya buka port yang benar-benar wajib untuk public.

Port 8080 (Dev Only):
🛑 BLOCK / INTERNAL ONLY
Port 443 (Production HTTPS):
✅ ALLOW PUBLIC
⚙️ Prinsip Least Exposure: Jangan gunakan konfigurasi firewall yang terlalu longgar secara gopoh.
Identiti & Akses

Authentication (Pengesahan Identiti)

Menjawab soalan utama: "Siapa anda?"

🔑 Kaedah Authentication
  • Username + Password
  • Multi-Factor Authentication (MFA / 2FA)
  • Passkey / Biometric
  • SSH Key Pair
  • Identity Provider (Google / GitHub SSO)
🔄 Aliran Kerja
Pengguna / Client ↓ 🔐 Authentication Check ↓ ✅ Identiti Disahkan ↓ Application
Identiti & Akses

Authorization (Kebenaran Akses)

Menjawab soalan seterusnya: "Apa yang anda dibenarkan buat?"

Selepas sistem tahu siapa anda (Authentication), sistem perlu menyemak peranan (role) anda untuk menentukan tindakan yang dibenarkan.

👑 Admin Role
  • ✓ Akses Dashboard Pentadbir
  • ✓ Padam / Edit Data Pengguna
  • ✓ Ubah Tetapan Server
👤 Normal User Role
  • ✓ Lihat Profil Sendiri
  • ❌ Dilarang Akses Admin Panel
  • ❌ Dilarang Ubah Settings Server
Perbandingan

Authentication vs Authorization

Dua konsep berbeza tetapi saling melengkapi

Kriteria Authentication (AuthN) Authorization (AuthZ)
Soalan Utama "Siapa anda?" (Who are you?) "Apa yang boleh anda buat?" (What can you do?)
Proses Menyemak kredensial (Login). Menyemak hak akses / kebenaran (Permissions).
Contoh Senario Pengguna berjaya login ke dalam akaun. ✅ Pengguna biasa cuba buka /admin → Ditolak (403 Forbidden). ❌
💡 Contoh Mudah: Kunci rumah ialah Authentication (membuktikan anda pemilik kunci). Bilik tidur mana yang anda boleh masuk ialah Authorization.
Prinsip Keselamatan #3

Principle of Least Privilege

"Berikan hanya kebenaran minima yang diperlukan sahaja."

❌ FULL ACCESS (Berbahaya)
████████████████ (Root / Full Control)

Aplikasi biasa diberikan akaun root. Jika aplikasi digodam, penyerang mendapat kawalan penuh ke atas seluruh server!

✅ REQUIRED ACCESS (Selamat)
████ (Read-Only)

Aplikasi hanya diberikan kebenaran membaca fail yang diperlukan sahaja tanpa kebenaran root atau menukar sistem.

Sistem Pengendalian

Linux User & Permissions

Mengapa aplikasi tidak sepatutnya dijalankan sebagai root

👥 Kategori Pengguna Linux
  • Owner (u): Pemilik fail.
  • Group (g): Kumpulan pengguna.
  • Others (o): Pengguna lain dalam sistem.
📜 Mod Kebenaran (Permissions)
  • Read (r): Kebenaran membaca fail.
  • Write (w): Kebenaran mengubah fail.
  • Execute (x): Kebenaran menjalankan program.
🛑 Amaran Penting: Jangan sesekali jalankan Python web server atau Docker container menggunakan akaun root! Gunakan dedicated service user (contoh: www-data atau appuser).
Pengurusan Server

SSH Security (Secure Shell)

Melindungi pintu utama pentadbiran server anda

🛡️ Asas Keselamatan SSH
  • ✅ Gunakan Key-Based Auth: Elakkan password authentication yang mudah diteka.
  • ✅ Disable Direct Root Login: Tetapkan PermitRootLogin no dalam SSH config.
  • ✅ Hadkan Akses IP: Hanya benarkan IP tertentu atau VPN jika boleh.
  • ✅ Update OpenSSH: Pastikan perisian SSH sentiasa mendapat patch terkini.
⚠️ Penting: Pastikan anda menguji sambungan SSH Key baharu dalam window kedua sebelum menukar/menutup konfigurasi lama untuk mengelakkan terkunci di luar (lockout)!
Kriptografi

SSH Key Architecture

Bagaimana Public & Private Key berfungsi bersama

Client (Laptop Anda) SSH Server (Remote) ┌───────────────────────┐ ┌───────────────────────┐ │ Private Key 🔑 │ ===========> │ Public Key 🔓 │ │ (SIMPAN RAHSIA!) │ (Verification) │ (~/.ssh/authorized_keys)│ └───────────────────────┘ └───────────────────────┘
🔑 Private Key
Tersimpan di laptop anda sahaja. Jangan pernah dikongsi atau muat naik ke mana-mana repository!
🔓 Public Key
Boleh diletakkan di server awam dengan selamat. Digunakan untuk menyemak ketulenan Private Key.
Kredensial

Password & MFA

Memperkemas kawalan akses pengguna

🔑 Kebersihan Kata Laluan
  • ✓ Gunakan kata laluan unik bagi setiap service.
  • ✓ Pastikan panjang minima 16+ aksara.
  • ✓ Gunakan Password Manager (Bitwarden / KeePass).
  • ❌ Jangan guna kata laluan yang sama!
🛡️ Multi-Factor Auth (MFA)

Memerlukan 2 bukti sebelum membenarkan akses:

Kata Laluan (Sesuatu yang anda tahu)
+
Authenticator App / Passkey (Sesuatu yang anda miliki)
Penyulitan Data

HTTPS / TLS

Melindungi data semasa transit dalam rangkaian

HTTP (Tidak Selamat) ❌
Data dihantar dalam bentuk teks biasa (Plaintext). Sesiapa dalam rangkaian boleh membaca kata laluan anda.
HTTPS (Encrypted) 🔒
Menggunakan penyulitan TLS. Menjamin Encryption, Authentication, dan Integrity.
⚠️ Penting: Cloudflare menyediakan HTTPS untuk sambungan ke browser. Walau bagaimanapun, HTTPS sahaja tidak bermaksud aplikasi di dalamnya automatik bebas daripada bug keselamatan!
Pengurusan Kredensial

Secrets Management

"Jangan Simpan Secret Dalam Source Code!"

❌ CONTOH SANGAT BERISIKO (Hardcoded Secret)
# JANGAN BUAT BEGINI DALAM KOD ANDA!
db_password = "SuperSecretPassword123" 
api_key = "CLOUDFLARE_API_TOKEN_XYZ"
✅ GUNAKAN PLACEHOLDER / ENV VARS
# Gunakan pembolehubah persekitaran
db_password = os.getenv("DATABASE_PASSWORD")
api_key = os.getenv("API_KEY")
Konfigurasi

Environment Variables (.env)

Memisahkan konfigurasi rahsia daripada kod sumber

📄 Fail .env (Simpan Luar Code)
APP_SECRET=<SECRET_TOKEN>
DATABASE_PASSWORD=<DB_PASSWORD>
DOMAIN=<DOMAIN_NAME>
🛡️ Perkara Wajib Dibuat
  • Tambah fail .env ke dalam .gitignore.
  • Jangan sekali-kali push .env ke GitHub/GitLab public.
  • Kawal kebenaran membaca fail .env di server.
💡 Realiti: Environment variables bukan perisai magis. Ia masih perlu dilindungi daripada akses tanpa kebenaran dan elakkan daripada dicetak dalam log aplikasi!
Penyelenggaraan

Software Updates & Patch Management

Menutup ruang kelemahan yang ditemui secara berkala

🧱 Lapisan Perisian yang Perlu Dikemaskini
OS (Ubuntu / Debian / AlmaLinux) └─ Package Manager (apt update && apt upgrade) └─ Application Engine (Python / Node.js / Docker) └─ Dependencies (pip / npm packages)
📢 Fakta: Server yang tidak dikemaskini lama-kelamaan akan mempunyai kerentanan keselamatan yang diketahui umum (Known Vulnerabilities / CVE).
Penyelenggaraan

Dependencies Management

Melindungi library pihak ketiga dalam aplikasi anda

📦 Rantaian Dependency
Python App ↓ Web Framework (Flask/FastAPI) ↓ Third-party Libraries

Jika satu sahaja library mempunyai security issue, keseluruhan aplikasi boleh terjejas.

✅ Amalan Penting
  • Pin versi spesifik (contoh: requirements.txt).
  • Kemaskini library secara berkala.
  • Semak notis keselamatan (Security Advisories).
  • Uji dalam persekitaran staging sebelum ke production.
Aplikasi

Application Security

Firewall tidak dapat membaiki kod aplikasi yang tidak selamat

🛠️ Elemen Penting Kod Selamat
  • ✅ Input Validation: Tapis semua input pengguna.
  • ✅ Secure Sessions: Gunakan HTTP-Only & Secure Cookies.
  • ✅ Safe Errors: Elakkan memaparkan stack trace kepada pengguna awam.
  • ✅ Secure Headers: Guna HSTS, CSP, X-Frame-Options.
  • ✅ Auth & AuthZ: Semak identiti pada setiap endpoint API.
🛡️ Prinsip: Firewall menapis lalu lintas luar, tetapi keselamatan aplikasi bergantung sepenuhnya pada kualiti dan ketelitian kod yang anda tulis.
Pangkalan Data

Database Security

Melindungi aset data terpenting anda

❌ Pendedahan Terus
Internet → Database (Port 3306)

Berisiko tinggi diserang secara brute force dari seluruh dunia!

✅ Seni Bina Terkawal
Internet → Application → Database

Database hanya mendengar pada IP dalaman (localhost / private network).

🔑 Langkah Tambahan: Gunakan kata laluan database yang kuat, tetapkan akaun akses khas dengan hak minima, dan buat salinan sandaran (backup) berjadual.

Admin Panel Security

Perlindungan berlapis untuk ruang kawalan utama

🛑 Jangan Berharap Pada "Secret URL" Sahaja

Mengubah URL dari /admin ke /my-secret-admin-123 (Security through obscurity) TIDAK mencukupi!

🔒 Kawalan Tambahan Wajib
  • Authentication Kuat + MFA
  • Authorization Semakan Role
  • Rate Limiting pada Cubaan Login
☁️ Perisai Cloudflare Access
User → Cloudflare Access → SSO Verification → Policy OK → Admin Panel
Kawalan Akses Perimeter

Cloudflare Access

Menambah lapisan pengesahan di awan sebelum sampai ke server

🔄 Aliran Trafik Cloudflare Access
Pengguna (Browser) ↓ ☁️ Cloudflare Edge Network ↓ 🔐 Pengesahan Identiti (Email Pin / Google SSO) ↓ 📋 Semakan Polisi Kebenaran (Is user allowed?) ↓ (JIKA LULUS) 🖥️ Application Server Anda
🎯 Kelebihan: Server tempatan anda tidak perlu melayan sebarang request daripada pengguna yang belum disahkan identitinya!
Model Keselamatan Moden

Zero Trust Architecture

"Never Trust, Always Verify"

🛡️ Konsep Zero Trust

Jangan anggap mana-mana pengguna atau peranti boleh dipercayai secara automatik hanya kerana mereka berada dalam rangkaian tertentu (contoh: Home Wi-Fi / VPN).


Setiap permintaan mesti disemak mengikut kriteria:

👤 Identity: Siapa pengguna ini?
💻 Device & Context: Adakah peranti ini selamat?
Keputusan Akhir pada Setiap Request: ALLOW atau DENY
Perlindungan Web

WAF (Web Application Firewall)

Menapis trafik HTTP/HTTPS yang mencurigakan

Internet ──> Cloudflare ──> [ WAF FILTER ] ──> Application Server │ (Trafik Jahat / Bot) 🛑 BLOCKED!
⚙️ Fungsi Utama WAF
  • Menapis corak serangan biasa pada HTTP request berdasarkan ruleset.
  • Menyekat bot automatik yang melakukan spamming atau scanning.
  • Memberikan perlindungan asas daripada serangan DDoS.
🛑 Ingat: WAF ialah lapisan pertahanan luaran, tetapi ia tidak menggantikan kewajipan menulis kod aplikasi yang selamat.
Seni Bina Keselamatan

Defense-in-Depth (Perlindungan Berlapis)

"Jangan bergantung kepada satu lapisan sahaja."

🌐 Internet ↓ 📡 DNS Security ↓ 🔒 HTTPS / TLS Encryption ↓ 🛡️ Cloudflare WAF ↓ 🔑 Cloudflare Access (Identity) ↓ 🔥 Server Firewall (UFW / IPTables) ↓ 🚇 Cloudflare Tunnel ↓ 🔐 Application Authentication & Authorization ↓ 🗄️ Database (Internal Only)
Visibility

Logging (Pencatatan Log)

"Kalau Tiada Log, Kita Buta."

📋 Log Penting Untuk Disimpan
  • Cubaan Login (Berjaya & Gagal).
  • Application Errors & Exceptions.
  • Status Pertukaran Service System.
  • Firewall Blocked Events.
🔍 Kenapa Log Penting?

Tanpa log, anda tidak akan tahu:

  • Siapa yang mengakses server.
  • Bila ralat bermula.
  • Punca sebenar kerosakan aplikasi.
⚠️ Privasi & Secret: Pastikan log anda TIDAK menyimpan kata laluan, API token, atau maklumat sensitif secara plaintext!

Pemulihan

Backup Strategy

"Security Tanpa Backup Masih Berisiko."

📋 Ciri-ciri Backup Yang Baik
  • ✅ Regular: Dijalankan secara automatik berjadual.
  • ✅ Tested: Diuji proses restore secara berkala.
  • ✅ Protected: Encrypted & dilindungi dari akses luar.
  • ✅ Separate: Disimpan di lokasi berasingan.
🔄 Aliran Pemulihan
Server Rosak / Terjejas ↓ 📦 Ambil Backup Terkini ↓ ⚙️ Restore Sistem ↓ ✅ Perkhidmatan Kembali Pulih
"Backup yang tidak pernah diuji restore bukanlah backup strategy yang lengkap."
Strategi Pemulihan

Prinsip 3-2-1 Backup

Standard amalan terbaik penyimpan data selamat

3
COPIES OF DATA

Simpan 1 data asal + 2 salinan sandaran.

2
DIFFERENT MEDIA

Gunakan 2 jenis media berbeza (contoh: SSD tempatan + NAS/Cloud).

1
OFFSITE COPY

Simpan sekurang-kurangnya 1 salinan di luar fizikal rumah/pejabat.

Respon Insiden

Incident Response Lifecycle

Langkah teratur apabila menghadapi masalah keselamatan

🚨 Incident Detected ↓ 🔍 1. Detection (Ketahui ada masalah) ↓ 🛑 2. Containment (Asingkan server / sekat akses terjejas) ↓ 🔬 3. Investigation (Kaji punca ralat melalui log) ↓ 🔄 4. Recovery (Restore daripada backup bersih & patch bug) ↓ 📝 5. Lessons Learned (Tingkatkan kawalan keselamatan)
Tindakan Defensive

Tindakan Jika Server Terkena Masalah

Apa yang perlu (dan tidak perlu) dilakukan

❌ JANGAN BUAT BEGINI
  • ❌ Panik dan buat tindakan melulu.
  • ❌ Padam semua log atau bukti persekitaran.
  • ❌ Tukar konfigurasi secara rawak tanpa rekod.
✅ TINDAKAN DEFENSIVE
  • ✓ Putuskan sambungan rangkaian (Isolate).
  • ✓ Simpan fail log penting untuk analisis.
  • ✓ Tukar kredensial & API token terjejas (Rotate).
  • ✓ Kemaskini patch & restore dari trusted backup.
