Asas Version Control

Apa Itu Git?

Git ialah Distributed Version Control System (DVCS) percuma dan open-source yang direka untuk mengendali projek perisian dari skala kecil hingga sangat besar.

Track Code Changes

Merakam setiap penambahan, pemotongan, dan perubahan baris kod berserta pengarang.

Collaboration

Membolehkan beratus developer bekerja serentak pada kod yang sama tanpa bertindih.

Branching & Merging

Membuat cabang eksperimen secara bebas dan menggabungkannya semula apabila selamat.

Real World Insight: Hampir 95%+ pasukan kejuruteraan perisian di seluruh dunia menggunakan Git sebagai tulang belakang pengurusan kod sumber mereka.
Kenapa Kena Ada Git?

Perbandingan: Tanpa vs Dengan Git

Tanpa Git (Pengurusan File Manual)
project_v1.py
project_v2_final.py
project_v2_really_final.py
project_v2_final_FIXED_TODAY.py
project_backup_dont_delete.py

Sukar tahu apa beza antara fail, tiada rekod siapa ubah, dan fail mudah terpadam.

Dengan Git (Commit History Clean)
commit c1d2e3f Add user authentication
commit a4b5c6d Fix database connection timeout
commit 7e8f9a0 Initial release v1.0.0

Satu directory sahaja! Setiap perubahan diikat dengan commit hash, timestamp, dan mesej bermakna.

Struktur Data

Apa Itu Git Repository?

Repository (Repo) ialah folder projek yang dipantau oleh Git. Di dalamnya terkandung folder tersembunyi .git/ yang menyimpan metadata, sejarah commit, branch, dan tags.

// Struktur Pohon Repository
my-app/
├── .git/ (Git Internal Database)
├── src/
├── main.py
└── auth.py
├── Dockerfile
└── README.md
Main / Master Branch Cabang utama yang mengandungi kod sedia-production yang stabil.
Feature Branches Cabang sampingan seperti feature/login untuk pembangunan fungsi baharu.
Release / Tags Penanda versi rasmi seperti v1.0.0.
3 Teras Utama Git

Working Directory, Staging Area & Repository

1. Working Directory

Unstaged Changes

Fail sedang diedit dalam editor kod korang. Git mengesan perubahan tapi belum bersedia disimpan.

2. Staging Area (Index)

Staged Files

Zon persediaan. Fail disaring menggunakan git add sebelum dimasukkan dalam commit.

3. Git Repository (.git)

Committed History

Snapshot kekal yang telah disahkan dengan git commit.

Working Dir git add Staging Area git commit Repository
Arahan Asas

`git status` — Semak Keadaan Repo

git status memberikan jawapan kepada soalan kritikal:
"Apakah status fail projek saya pada saat ini?"

Untracked Files: Fail baharu yang belum pernah ditambah ke Git.
Modified Files: Fail sedia ada yang telah diubah suai.
Changes to be committed: Fail yang sudah berada di Staging Area.
$ git status
On branch main
Changes not staged for commit:
modified: app.py
Untracked files:
utils/helper.py
Penyediaan Snapshot

`git add` — Pindah ke Staging Area

// Tambah fail spesifik
$ git add app.py
// Tambah SEMUA perubahan folder semasa
$ git add .
PERATURAN PENTING: git add TIDAK bermaksud perubahan anda telah selamat disimpan dalam sejarah (history) repo! Ia sekadar memasukkan fail ke dalam kotak persediaan (Staging Area).

Tips Best Practice:

Gunakan git add app.py berbanding git add . jika anda ingin mengasingkan commit bagi tujuan komit bersih (atomic commits).

Merakam Sejarah

`git commit` — Merakam Snapshot Permanent

Commit ialah Snapshot / Rekod Kekal perubahan yang disimpan dalam pangkalan data Git. Setiap commit mendapat penanda unik 40-karakter (SHA-1 Hash).

// Format Standard
$ git commit -m "feat: add user login endpoint"

Ciri Mesej Commit Yang Baik:

  • Jelas, padat, dan menceritakan APA dan KENAPA perubahan dibuat.
  • Gunakan perkataan kata kerja perintah: Add login bukannya Added login.
  • Boleh mengikut spesifikasi Conventional Commits (feat:, fix:, docs:).
Menyemak Log Sejarah

`git log` — Audit Trail Perubahan

$ git log --oneline
a1b2c3d Add user authentication JWT
d4e5f6a Add health check API route
1234567 Initial commit & project setup
Audit & Debugging Membolehkan pasukan mengesan punca bug diperkenalkan secara tepat.
Rollback Safe Point Setiap hash commit (a1b2c3d) membolehkan kita mengembalikan sistem ke keadaan tersebut jika production rosak.
Pemeriksaan Baris Kod

`git diff` — Membanding Perubahan Baris

git diff memaparkan perbezaan persis antara fail di Working Directory dengan fail di Staging Area / Commit Terakhir.

$ git diff app.py
--- a/app.py
+++ b/app.py
- PORT = 8080
+ PORT = 3000
+ DEBUG = False
Pedagogy Breakdown:

WHAT: Alat perbandingan kod grafik/tekstual.

WHY: Mengelakkan ter-commit kod salah, secret kunci API, atau kenyataan `print()` debug yang tertinggal.

HOW: Membandingkan versi hash dalam blob Git.

Pengasingan Kod

Apa Itu Git Branch?

Branch (Cabang) ialah penunjuk boleh alih (*movable pointer*) ke salah satu commit. Ia membolehkan developer membina feature baharu tanpa mengganggu cawangan utama (main).

main ──── [C1] ─── [C2] ───────────────── [C5 (Merge)]
└─ feature/login ─── [C3] ─── [C4] ──┘
Independent Line of Development Ujian atau eksperimen yang gagal di branch feature boleh dipadam secara terus tanpa merosakkan main.
Parallel Work 10 orang developer boleh membuat 10 feature berbeza serentak pada branch tersendiri.
Strategi Cawangan

Main Branch vs Feature Branch

Main Branch (Production)

  • Menyimpan kod yang stabil, diuji, dan sedia dideploy.
  • Dilarang push secara terus (*Protected Branch*).
  • Hanya menerima perubahan melalui Pull Request (PR) yang diluluskan.

Feature Branch (Development)

  • Dicipta khas untuk satu tugasan (contoh: feature/login-ui).
  • Bersifat sementara — dipadam selepas digabungkan (*merged*) ke main.
  • Tempat bebas melakukan eksperimen tanpa risiko downtime.
Navigasi Branch

`git switch` — Berpindah Branch

// Cipta dan terus pindah ke branch baharu
$ git switch -c feature/login
// Berpindah semula ke main branch
$ git switch main

Nota Perintah Moden vs Lama:

Dahulu perintah git checkout -b digunakan. Git versi moden memperkenalkan git switch khusus untuk navigasi branch supaya lebih jelas.

Penggabungan Kod

`git merge` — Menggabungkan Branch

Penggabungan (*Merging*) mengambil sejarah commit daripada branch feature dan memasukkannya ke dalam branch sasaran (contohnya main).

// 1. Berpindah ke main dahulu
$ git switch main
// 2. Gabungkan feature branch
$ git merge feature/login

Jenis Merge:

Fast-Forward Merge: Main tiada commit baharu, pointer hanya dialih ke depan.

3-Way Merge: Kedua-dua branch ada commit baharu. Git secara automatik mencipta Merge Commit khas.

Konflik Kod

Merge Conflict — Punca & Penyelesaian

Skenario Konflik:

Developer A dan Developer B mengubah baris kod yang SAMA pada fail yang SAMA secara serentak.

<<<<<<< HEAD (Branch Anda)
port = 8080
=======
port = 9090
>>>>>>> feature/api

Langkah Penyelesaian Manusia (Manual):

1. Buka fail berkonflik dalam VS Code / Editor.
2. Bincang dengan rakan pasukan & pilih kod yang betul.
3. Padamkan tanda konflik (<<< === >>>).
4. Jalankan git add . dan git commit untuk menyelesaikan merge.
Mekanisme Pengawasan

Apa Itu Pull Request (PR) / Merge Request (MR)?

Pull Request (di GitHub) atau Merge Request (di GitLab) ialah cadangan untuk menggabungkan perbezaan kod dari branch feature anda ke dalam main branch projek.

1. Push Feature Branch
2. Cipta Pull Request
3. Automated CI Pass
4. Peer Code Review
5. Merge ke Main
Kawalan Kualiti

Budaya Code Review

Apa Yang Diperiksa Oleh Reviewer?

Keselamatan (Security): Tiada kredensial/secret terdedah, perlindungan dari SQLi/XSS.
Prestasi (Performance): Query pangkalan data yang cekap tanpa kebocoran memori.
Keterbacaan (Readability): Mengikut standard linting pasukan.

"Code review bukan persidangan mencari siapa salah. Ia mekanisme menangkap bug sebelum ia sampai ke tangan pelanggan."

Penanda Versi

`git tag` — Penanda Milestone Release

Tag digunakan untuk memberi penanda tetap pada commit tertentu dalam sejarah (kebiasaannya penanda rilis seperti v1.0.0).

// Cipta tag berserta mesej
$ git tag -a v1.0.0 -m "Release version 1.0.0"
// Push tag ke remote server
$ git push origin v1.0.0

Kenapa Tag Sangat Penting Dalam CI/CD?

Pushing tag baru (contoh: v1.2.0) selalunya dijadikan pemicu (*trigger*) automatik untuk pipeline CD membina Docker Image dan mendepoy ke Production Server!

Pemiawaian Versi

Semantic Versioning (SemVer)

MAJOR.MINOR.PATCH
Contoh: v2.4.1
MAJOR (2.0.0) Perubahan besar yang tidak serasi dengan versi terdahulu (*Breaking Changes*).
MINOR (2.4.0) Penambahan feature baharu yang masih serasi ke belakang (*Backward Compatible*).
PATCH (2.4.1) Pembaikan bug kecil (*Bug Fixes*) tanpa penambahan feature.
GitHub vs Git

Remote Repository (GitHub / GitLab)

Local vs Remote:

Local Repo: Tersimpan dalam pemacu keras (HDD/SSD) komputer anda.

Remote Repo: Dihoskan di pelayan awan seperti GitHub, GitLab, atau Bitbucket.

// Tambah remote origin
$ git remote add origin https://github.com/example/myapp.git
KONSEP PENTING:

Git ialah *tool/software* version control.

GitHub / GitLab ialah *platform perkhidmatan web* yang menyimpan Git repository di cloud berserta kemudahan UI, CI/CD runner, dan Issue Tracker.

Sinkronisasi

`git push` vs `git pull`

git push

Hantar commit tempatan dari komputer anda ke Remote Repository (GitHub).

$ git push origin main

git pull

Muat turun dan **terus gabungkan** commit terkini dari Remote ke Local branch anda.

$ git pull origin main
Sinkronisasi Selamat

`git fetch` — Semak Tanpa Menggabung

Berbeza dengan git pull, perintah git fetch mengambil maklumat terkini dari remote **TANPA** terus mengubah atau mengacau kod di working branch anda.

$ git fetch origin
// Semak perbezaan dahulu
$ git diff main origin/main

Persamaan Formula:

git pull = git fetch + git merge

Gunakan git fetch jika anda ingin menyemak perubahan rakan pasukan secara selamat sebelum memutuskan untuk merge.

Penyaringan Fail

`.gitignore` — Abaikan Fail Sampah

// Contoh fail .gitignore
.env
__pycache__/
*.log
node_modules/
.venv/
dist/
Jangan Push Dependency / Cache! Folder seperti node_modules/ bersatu gigabyte tidak sepatutnya berada dalam Git repository.
Abaikan Fail Kredensial Tempatkan Fail .env tempatan wajib dimasukkan ke `.gitignore`!
Keselamatan Amaran Tinggi

Secret Management Dalam Git

❌ JANGAN PERNAH COMMIT SECRETS:

  • Kata Laluan Pangkalan Data
  • API Keys (AWS, OpenAI, Cloudflare)
  • Kunci SSH Private Key / Token JWT

✓ GUNAKAN PENYELUTURAN SECURE:

  • Environment Variables (process.env)
  • GitHub / GitLab Repository Secrets
  • Vault Services (HashiCorp Vault, AWS Secrets Manager)
INGATAN PENTING: ".gitignore bukanlah Secret Manager!" Sekiranya secret pernah ter-commit secara tidak sengaja, hash tersebut kekal berada dalam Git history walaupun fail telah dipadam. Secret tersebut dikira terbocor dan **WAJIB DI-ROTATE** segera.

Pemeriksaan Statik

Apa Itu Linting & Static Analysis?

Linter menyemak kod sumber anda **tanpa menjalankan kod tersebut** untuk menangkap ralat sintaks, pembolehubah yang tidak digunakan, atau perlanggaran gaya penulisan.

Python Ecosystem: ruff, flake8, black
JavaScript / Node.js: eslint, prettier
PERINGATAN PEDAGOGI: Jangan sesekali menganggap Linter sebagai pengganti Automated Testing! Linter hanya menyemak format dan sintaks, bukannya logik perniagaan (*business logic*) aplikasi.
Pengujian Otomatik

Jenis-Jenis Automated Testing

1. Unit Test

Menguji fungsi atau kaedah kecil secara terpencil. Sangat pantas dijalankan (milisaat).

2. Integration Test

Menguji perhubungan antara komponen (contoh: API app berkomunikasi dengan pangkalan data PostgreSQL).

3. End-to-End (E2E) Test

Simulasi tingkah laku pengguna sebenar dari Frontend hingga Backend (menggunakan Playwright / Cypress).

Strategi Ujian

Piramid Ujian (Test Pyramid)

E2E Tests (Sedikit)
Integration Tests (Sederhana)
Unit Tests (Banyak, Pantas & Murah)

Piramid ujian memberi panduan nisbah ujian yang ideal dalam pipeline CI.

  • Unit Tests di dasar: Kerana ia murah, sangat pantas, dan mudah diselenggara.
  • E2E di puncak: Kerana ia lambat, mahal, dan mudah terganggu (*flaky*).
Fasa Kompilasi

Fasa Build & Artifact

Selepas kod lulus ujian, CI akan mengompil atau membungkus kod sumber menjadi **Artifact** yang sedia untuk dideploy.

// Tradisional: Zip / Binary

// Moden (Container Era):

Prinsip Immutability:

Artifact yang dibina dalam CI tidak boleh diubah lagi. Artifact yang sama yang diuji dalam Staging adalah artifact persis yang dideploy ke Production!

Standard Container

Docker Image Sebagai CI Artifact

PERATURAN TAG PRODUCTION:

Sentiasa gunakan tag spesifik berangka seperti :1.2.0 atau SHA commit :a1b2c3d bagi tujuan keterulangan (*reproducibility*) dan rollback.

Praktikal Self-Hosted

Deployment Ke Home Server / Raspberry Pi

Aliran Kerja Home Server:

  1. GitHub Actions membina Docker Image berasaskan seni bina ARM/x86.
  2. Image di-push ke GitHub Container Registry.
  3. GitHub Actions menghantar isyarat Webhook / SSH ke Raspberry Pi tempatan.

// Skrip Deployment pada Server

$ docker compose up -d --remove-orphans
// Semak status container

Strategi Deployment

4 Strategi Deployment Utama

1. Recreate Matikan container lama, kemudian hidupkan container baru. Ada downtime seketika.
2. Rolling Update Gantikan pod/container satu demi satu secara berperingkat tanpa downtime.
3. Blue / Green Sediakan dua environment identikal. Tukar trafik dari Blue ke Green serta-merta.
4. Canary Salurkan 5% trafik pengguna ke versi baru dahulu untuk menguji kestabilan sebelum 100%.
Strategi Asas

Strategi 1: Recreate

Old Container ──► STOP & REMOVE ──► Start New Container

Sesuai untuk persekitaran Development / Staging atau aplikasi dalaman yang boleh menerima downtime beberapa minit.

Kelebihan: Sangat mudah dibina, tiada isu persaingan versi pangkalan data.
Kekurangan: Menimbulkan Service Downtime kepada pengguna sepanjang proses pengangkatan.
Zero Downtime

Strategi 2: Blue / Green Deployment

BLUE Environment

Versi v1.0.0 (Sedang Menerima Trafik Pengguna)

Reverse Proxy Switch (Nginx / Cloudflare)
GREEN Environment

Versi v1.1.0 (Diuji Kesihatan & Sedia Diswitch)

Jika Green bermasalah, titikkan (*point*) semula Reverse Proxy ke Blue dalam masa kurang 1 saat!

Pengurangan Risiko

Strategi 3: Canary Deployment

Pembahagian Trafik Berperingkat:

Fasa 1: 95% Trafik v1.0 | 5% Trafik Canary v2.0
Fasa 2: 80% Trafik v1.0 | 20% Trafik Canary v2.0
Fasa 3: 0% Trafik v1.0 | 100% Trafik v2.0
Asal Usul Nama:

Diambil dari burung *Canary in a Coal Mine*. Jika terdapat bug kritikal dalam v2.0, hanya 5% pengguna terkesan sebelum ia ditarik balik dengan selamat.

Pengesahan Keadaan

Health Check Selepas Deployment

Container "Running" ≠ App "Berfungsi"!

Container Docker boleh berstatus Up 2 minutes, tetapi aplikasi di dalamnya pengsan akibat kehabisan memori atau gagal berhubung dengan DB.

// Skrip Semakan HTTP dalam CD
$ curl -f http://localhost:3000/health || exit 1
// Respons Dijangka:
{"status": "ok", "db": "connected"}
Pemulihan Bencana

Automatic Rollback

Deploy Versi v1.5.0
Health Check Gagal (HTTP 500)
Trigger Auto Rollback
Kembali ke Versi v1.4.2

Automated Rollback memastikan insiden masa terhenti (*downtime*) dikurangkan daripada berjam-jam kepada hanya beberapa saat sahaja!

Prinsip Keselamatan

Principle of Least Privilege (PoLP)

❌ AMALAN BURUK:

Memberi CI Runner akses penuh root / sudo pada seluruh server production.

✓ AMALAN TERBAIK (PoLP):

Cipta AKAUN KHAS yang hanya dibenarkan melepaskan arahan docker pull dan docker compose up sahaja.

Kredensial Capaian

Pengurusan Deployment Credentials

Checklist Keselamatan Kredensial Deploy:

  • Gunakan Short-Lived Tokens: Akses sementara (contoh: OIDC / AWS STS) berbanding SSH key kekal.
  • Scoped Permissions: Token hanya boleh push ke satu repository Docker spesifik sahaja.
  • Kunci SSH Terhad: Gunakan `command="..."` dalam fail authorized_keys untuk menyekat shell interaktif.

Jika ujian unit atau imbasan keselamatan gagal pada mana-mana peringkat, pipeline **WAJIB TERHENTI SEGERA (Pipeline Halt)**.

[Lint: PASS] ──► [Unit Test: FAIL ❌] ──► 🛑 PIPELINE TERMINATED
Pemeriksaan Kerentanan

Imbasan Keselamatan Docker Image

// Imbasan Kerentanan Guna Trivy
$ trivy image myapp:1.0.0

Tujuan Imbasan:

Mengespesifikasi CVE (Common Vulnerabilities and Exposures) dalam OS base image sebelum dideploy ke server.

Pakej Pihak Ketiga

Dependency Scanning

Aplikasi anda bergantung kepada ratusan library pihak ketiga (pip, npm). CI boleh mengimbas fail manifest secara automatik.

Tools: GitHub Dependabot / Snyk / OWASP Dependency-Check
Pencegahan Kebocoran

Secret Scanning Automatik

Mencegah Token Terbocor:

Secret scanner (seperti GitGuardian / Trufflehog) akan menolak Git Push jika dikesan corak Kunci API atau Password terbocor.

Peraturan Repo

Branch Protection Rules

Peraturan Wajib Main Branch:

  • ✓ Pull Request Diperlukan (Tiada Direct Push).
  • ✓ Sekurang-kurangnya 1 Code Reviewer meluluskan.
  • ✓ CI Pipeline mesti Pass 100%.
  • ✓ Force Push (git push -f) Dilarang Sama Sekali.

Pemulihan Pantas

Konsep Pelaksanaan Rollback

Rollback bukan bermaksud membuat commit baru secara tergesa-gesa. Ia bermaksud mengarahkan CD **menukar semula penunjuk tag Docker Image** ke versi terdahulu yang diketahui stabil.

Migrasi Skema

Database Migration Dalam CI/CD

Strategi Backward-Compatible:

1. Tambah lajur DB baharu dahulu (Jangan padam lajur lama lagi).

2. Deploy aplikasi v2 yang membaca lajur baharu.

3. Padam lajur lama dalam release akan datang.

AMARAN ISU MIGRASI: Migrasi skema DB yang tidak serasi ke belakang akan menyebabkan rollback aplikasi v1 gagal berhubung dengan DB!
Ketersediaan Tinggi

Mencapai Zero Downtime Deployment

3 Komponen Utama Zero Downtime:

  • Reverse Proxy (Nginx/Traefik) dengan *Graceful Reload*.
  • Aplikasi menyokong *Graceful Shutdown* (menyiapkan request sedia ada sebelum mati).
  • Health Check Probe yang betul.

Dokumentasi Deployment

Setiap projek wajib mempunyai fail DEPLOYMENT.md yang menerangkan:

  • Cara manual triggered rollback.
  • Senarai Environment Variables yang diperlukan.
  • Langkah pemulihan bencana pangkalan data.
Panduan Kecemasan

Contoh Deployment Runbook

// RUNBOOK: DEPLOYMENT FAILURE
1. Semak status Grafana Alerting.
2. Jika HTTP 5xx > 5%, jalankan: `gh workflow run rollback.yml`
3. Sahkan kesihatan server kembali ke v1.4.2.
4. Buka ticket insiden Post-Mortem.
