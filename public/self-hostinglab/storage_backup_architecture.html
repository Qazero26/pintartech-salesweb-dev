SLIDE 2

Kenapa Storage Penting?

Aplikasi moden sentiasa menghasilkan dan memproses data. Tanpa storage yang betul, state aplikasi akan hilang apabila container/server terhenti.

Data yang Disimpan oleh Aplikasi:

  • Users & Profil Akaun
  • Photos & Media Uploads
  • Documents & Fail Pengguna
  • Databases (SQL / NoSQL)
  • System & Access Logs
  • Configuration Files
  • Automated Backups
Application (Stateless / Code)
Data (Stateful Payload)
Storage System (Physical / Volume)
Peringatan Kebolehan: Jika storage gagal, application mungkin masih hidup (code tetap berjalan), tetapi perniagaan terhenti kerana data hilang!
SLIDE 3

Perbezaan Asas: Storage vs Backup

Dua istilah ini kerap dicampur adak, namun peranan dan cirinya bertentangan secara fundamental.

STORAGE

"Tempat data sedang AKTIF digunakan oleh sistem."

Fokus: Performance, Low Latency, High IOPS.

Operasi: Read & Write berterusan oleh aplikasi.

Contoh: Database yang dipasang pada SSD server (`/var/lib/postgresql/data`).

BACKUP

"SALINAN data berasingan khusus untuk pemulihan (Recovery)."

Fokus: Safety, Retention, Isolation, Encryption.

Operasi: Writable secara terjadual, read hanya semasa disaster/test.

Contoh: Fail `.tar.gz` atau Restic repository yang disalin ke NAS / Cloud Object Storage.

Database NVMe SSD = STORAGE
vs
Database Dump External/Offsite Drive = BACKUP
SLIDE 4

Storage Layers Architecture

Data bergerak melalui pelbagai lapisan daripada perkakas fizikal sehingga ke aplikasi.

Application Layer Docker App / Postgres
Filesystem Layer ext4 / XFS / Btrfs
Volume Layer Docker Volume / Partition
Block Device Layer /dev/sda / /dev/nvme0n1
Physical Controller / Media NVMe Controller / Flash NAND

Penerangan Lapisan:

Aplikasi tidak menulis data terus ke kepingan silikon. Ia berhubung dengan Filesystem yang menstrukturkan bait kepada fail. Filesystem dipasang pada Volume/Partition yang mengambil raw blocks daripada Block Device, yang diuruskan oleh pengawal hardware SSD/HDD.

PENTING: Kegagalan boleh berlaku pada mana-mana satu lapisan ini!
SLIDE 5

HDD vs SSD Architecture

HDD (Hard Disk Drive)

  • Component fizikal bergerak (Mekanikal, Platter & Read/Write head).
  • Sangat murah mengikut kapasiti per-TB.
  • Sesuai untuk Bulk Storage, Archives, Video Media Server.
  • Slow random access (High Latency due to seek time).

SSD (Solid State Drive)

  • Memory Flash NAND (Tiada komponen fizikal bergerak).
  • Extremely fast random access (Ultra low latency).
  • Ideal untuk Databases, OS Drive, Container Runtime.
  • Harga lebih tinggi per-TB berbanding HDD.
Prinsip Reka Bentuk: SSD tidak sentiasa jawapan untuk semua workload. Gunakan SSD untuk performance-critical data (Databases) dan HDD untuk kapasiti besar (Backups, Cold Storage).
SLIDE 6

Storage Capacity vs Performance

Standard NAS Drive

16 TB

HDD (7200 RPM)

NVMe OS Drive

1 TB

PCIe Gen4 SSD

Mitos: Storage besar tidak bermaksud storage laju!

HDD 16TB mampu menyimpan bertan-tan fail backup, namun apabila dieksekusi query database PostgreSQL yang kompleks, latency boleh melonjak tinggi.

Formula Metric Utama:

Capacity (Kapasiti)

Berapa banyak data yang Boleh disetor (TB, PB).

Throughput (Kadar Pemindahan)

Berapa cepat data boleh dipindahkan secara berterusan (MB/s, GB/s).

IOPS (Input/Output Operations Per Second)

Berapa banyak operasi kecil read/write boleh berlaku dalam 1 saat.

SLIDE 7

IOPS vs Throughput

IOPS (Random I/O)

Bilangan operasi baca/tulis saiz kecil (contoh: 4KB blocks) setiap saat.

Sangat Penting Untuk:

• Database OLTP (PostgreSQL, MySQL)

• Virtual Machine / Container Volumes

Throughput (Sequential I/O)

Volume data keseluruhan yang boleh dipindahkan dalam satu julat masa (MB/s).

Sangat Penting Untuk:

• Large Backup Stream (.tar files)

• Video Streaming & Bulk Media Transfer

SLIDE 8

Storage Latency Impact

Latency storage adalah masa yang diambil oleh perkakas storage untuk membalas permintaan I/O tunggal.

NVMe SSD < 0.1 ms Latency

Aplikasi bertindak balas serta-merta. Query database siap dalam beberapa milisaat.

HDD / High Latency Storage 10 - 20 ms Latency

I/O bottleneck! Thread aplikasi tersumbat (I/O Wait tinggi) menunggu jawapan disk.

Low Latency Storage = Low CPU I/O Wait = Fast Web Response Time
SLIDE 9

Filesystem Overview

Filesystem bertindak seperti indeks perpustakaan. Ia mengatur bagaimana data disimpan, dicari dan diuruskan pada disk.

ext4

Standard Linux Filesystem

Sangat stabil, diuji bertahun-tahun, pilihan default untuk kebanyakan distro Linux & server.

XFS

High-Performance File System

Cemerlang mengendalikan fail bersaiz sangat besar dan parallel I/O workloads (RHEL Default).

Btrfs / ZFS

Advanced Copy-on-Write (CoW)

Menyokong built-in Snapshot, Raid, Checksumming dan Self-healing data corruption.

Mount Point Explained

Mount point ialah folder tertentu dalam Linux directory tree tempat di mana sesuatu storage partition dicantumkan.

/ (Root Directory)

├── /var/lib/docker (Mounted on Primary SSD)

├── /data (Mounted on Dedicated High-Speed Disk)

├── /data/database

└── /mnt/backup (Mounted via Network/NAS)

SLIDE 12

File Storage Architecture

Structural Hierarchical

Data diatur dalam struktur hirarki Folder & Directory. Diakses menggunakan path unik seperti `/var/log/nginx/access.log`.

Contoh Penggunaan:

• Local Linux Filesystem

• Network Attached Storage (NAS)

• Shared Folders (NFS / SMB)

Kelebihan & Kekurangan:

Mudah difahami oleh manusia & OS secara native.

Sukar untuk scale apabila fail mencecah puluhan juta (directory lookup slow).

SLIDE 13

Block Storage Architecture

Block Storage menyediakan storage dalam bentuk blok mentah (raw blocks). Tiada konsep fail atau folder sehinggalah anda formatnya dengan filesystem.

Block Storage Volume (/dev/sdb)
Format (ext4 / XFS)
Ready Files & Directories

Ciri Utama:

• Ultra-low latency & high performance.

• Boleh di-attach ke virtual machine (Contoh: AWS EBS, Cloud Volume).

SLIDE 14

Object Storage Architecture

Object Storage menyimpan data sebagai "Object" tidak berstruktur yang dilabel bersama Metadata dan Key unik. Diakses menggunakan API (HTTP/REST S3 API).

Object Payload
Key: backups/db-2026-08-19.tar.gz
Metadata: { "encrypted": "true", "owner": "admin" }
Data: [ Binary Data Stream ]

Kegunaan Ideal:

• Offsite Backups & Archives (Restic / Borg targets)

• Unstructured Media (Photos, Videos, User Uploads)

• Highly Scalable (Petabyte-scale tanpa masalah hierarchy)

SLIDE 16

Docker Storage Architecture

Container filesystem secara laluan asal (Writable Layer) adalah ephemeral. Apabila container dipadam, data di dalam Writable Layer akan musnah sepenuhnya.

Writable Layer (Ephemeral)

Data ditulis terus di dalam container instance. Boleh rosak atau terpadam jika container di-recreate!

Persistent Storage (Volume / Bind Mount)

Data disimpan terpisah di luar container cycle pada host disk. Data kekal walaupun container dimatikan.

SLIDE 17

Docker Managed Volume

PostgreSQL Container
Docker Volume (pg_data)
Host Storage (/var/lib/docker/volumes/...)
AMARAN PENTING: Docker Volume ≠ Backup! Volume hanyalah persistent local storage. Jika disk host terbakar, Docker volume turut musnah!
SLIDE 18

Docker Bind Mount

Bind mount memetakan mana-mana folder khusus di Host OS terus ke dalam lokasi folder dalam Container.

Host Path: /srv/app/config.json

↓ MAPPED TO ↓

Container Path: /app/config.json

Sangat berguna untuk config file, source code semasa development, dan mount khusus pada disk luaran.

SLIDE 19

Database Storage Requirements

Database memerlukan kawalan I/O yang sangat stabil dan pantas (ACID compliance).

Faktor Prestasi Utama:

• Low Latency NVMe SSD: Menghindari bottleneck transaksi.

• High Random IOPS: Membolehkan pembacaan & penulisan serentak.

• WAL (Write-Ahead Logging): Memerlukan penulisan sequential yang cepat ke disk.

Risiko Storage DB:

• Jangan letak live DB data di atas Network Drive (NFS) berkualiti rendah kerana risiko lock failure & latency tinggi.

SLIDE 20

RAID (Redundant Array of Independent Disks)

RAID menggabungkan beberapa physical disk menjadi satu logical storage unit untuk Performance, Redundancy atau gabungan kedua-duanya.

Mantra Terpenting Infrastructure:

"RAID BUKAN BACKUP!"

RAID melindungi sistem anda daripada kegagalan perkakas disk (Hardware Fault Tolerance), tetapi TIDAK melindungi daripada pemadaman tidak sengaja atau kerosakan fail.

SLIDE 21

Tahap-Tahap RAID (RAID Levels)

RAID 0 (Striping)

Performance maksimum. TIADA Redundancy. 1 disk rosak = Semua data hilang!

RAID 1 (Mirroring)

Salinan pendua 1:1 pada disk kedua. Redundancy tinggi. Tolerate 1 disk failure.

RAID 5 (Parity)

Menggunakan parity disebar pada minimum 3 disk. Boleh survive 1 disk failure.

RAID 6 (Dual Parity)

Menggunakan dual parity pada min 4 disk. Boleh survive 2 disk failure serentak.

RAID 10 (1+0 Striped Mirrors)

Gabungan kelajuan RAID 0 dan ketahanan RAID 1. Pilihan popular untuk server database production.

SLIDE 22

Simulasi Senario: RAID vs Backup

Senario 1: Disks 1 Terbakar / Rosak

RAID 1/5/10: BERJAYA! Sistem kekal dalam keadaan Uptime/Available. Disk rosak dikeluarkan & diganti.

Senario 2: Admin Terpadam Database (`DROP DATABASE production;`)

RAID: GAGAL! Pemadaman serta-merta ditulis ke kesemua disk RAID!
BACKUP: BERJAYA! Boleh restore semula dump snapshot dari malam sebelumnya.
"RAID menjaga High Availability. Backup menjaga Disaster Recovery."
SLIDE 23

Apa itu Snapshot?

Snapshot ialah gambaran keadaan sistem pada satu titik masa khusus (Point-in-Time Read-Only Frozen View).

10:00 AM Snapshot A Created
11:00 AM System Upgrade Executed
11:05 AM Instant Rollback to Snapshot A

Sangat bermanfaat untuk pengujian pantas sebelum OS/App upgrade. Namun, jika storage utama rosak, snapshot di dalam storage itu turut musnah.

SLIDE 24

Snapshot vs Backup

SNAPSHOT

• Sangat pantas dicipta (hampir instant via Copy-on-Write).

• Masih bergantung pada storage asal / underlying disk pool.

• Utama untuk local rollback pantas.

BACKUP

• Mengambil masa lebih lama bergantung saiz data.

• Salinan kendiri yang dipindahkan ke medium/lokasi berasingan.

• Utama untuk pemulihan bencana (Disaster Recovery).

SLIDE 25

Data Replication

Replication ialah proses menyalin perubahan data dari Primary Server ke Replica/Secondary Server secara terus (Synchronous atau Asynchronous).

Primary Database Server
Replica Database Server

Gunaan utama: Read Scaling (mengurangkan beban primary) dan Failover High Availability.

SLIDE 26

Kenapa Replication Bukan Backup?

Replication Menyebarkan Kesilapan (Replicates Mistakes)

Jika virus merebak, data terpadam atau database mengalami corrupt data di Primary Server, mekanisme replication akan menyalin kerosakan tersebut ke Replica Server dalam hitungan saat!

Primary: DELETE * FROM users; ----(Replicated)----> Replica: DELETE * FROM users;
SLIDE 27

Apa itu Backup?

Backup ialah salinan data lengkap, selamat dan konsisten dari masa lampau yang diasingkan daripada infrastruktur pengeluaran (Production).

Data Integrity

Data telah di-verify dan di-encrypt.

Historical Point

Boleh dipulihkan mengikut garis masa (Point-in-time).

Isolated Storage

Disimpan di peranti atau lokasi offsite berasingan.

SLIDE 28

Full Backup

Menyalin keseluruhan set data dari awal sehingga akhir tanpa terkecuali.

Kelebihan:

• Proses restore sangat mudah & pantas (Hanya perlukan 1 fail archive ini sahaja).

Kekurangan:

• Memakan saiz storage yang sangat besar.

• Proses backup mengambil masa yang paling lama.

SLIDE 29

Incremental Backup

Hanya menyalin data yang BERUBAH SEJAK BACKUP TERAKHIR (Sama ada Full atau Incremental sebelumnya).

Ahad: FULL BACKUP (100 GB)

Isnin: INCREMENTAL (Perubahan Isnin = 2 GB)

Selasa: INCREMENTAL (Perubahan Selasa sahaja = 3 GB)

Untuk Restore Selasa: Memerlukan Full Ahad + Incremental Isnin + Incremental Selasa!

SLIDE 30

Differential Backup

Menyalin semua data yang BERUBAH SEJAK FULL BACKUP TERAKHIR.

Ahad: FULL BACKUP (100 GB)

Isnin: DIFFERENTIAL (Perubahan Isnin = 2 GB)

Selasa: DIFFERENTIAL (Perubahan Isnin + Selasa = 5 GB)

Untuk Restore Selasa: Hanya perlukan Full Ahad + Differential Selasa!

SLIDE 31

Ringkasan Jenis Backup

Jenis Backup Kelajuan Backup Saiz Storage Kelajuan Restore
Full Paling Perlahan Paling Besar Paling Terpantas (1 File)
Incremental Paling Pantas Paling Kecil Perlahan (Perlu Restore Chain)
Differential Sederhana Sederhana Pantas (Full + 1 Diff)
SLIDE 32

Strategi Backup 3-2-1

Standard emas industri dalam memastikan ketahanan data daripada sebarang bencana local.

3

Salinan Data (Copies)

1 Live Production + 2 Backup Copies.

2

Medium Berbeza

Contoh: Local NVMe SSD + Local NAS Hard Drive.

1

Salinan Offsite

1 salinan disimpan di lokasi geografi berasingan (Cloud S3).

SLIDE 33

Konsep Lanjutan: 3-2-1-1-0

3 Copies of Data
2 Different Media
1 Offsite Storage
1 Offline / Immutable Copy
0 Restore Errors (Verified)

Standard perusahaan terbaik untuk bertahan daripada serangan Ransomware moden.

SLIDE 34

Offsite Backup

Memindahkan salinan backup ke bangunan atau rantau awan (Cloud Region) yang berbeza.

Home Server / Datacenter A
Cloud Object Storage / Remote Server B

Melindungi perniagaan daripada bencana fizikal setempat seperti Kebakaran, Banjir, Kecurian, dan Kerosakan Elektrik Total.

SLIDE 35

Offline Backup (Air-Gapped)

Fizikal Air-Gap

Backup dicipta ke external hard drive/tape, kemudian kabel di-unplug secara fizikal. Media ini disimpan dalam peti besi. Hacker yang memenceroboh rangkaian server TIDAK BOLEH memadam drive ini secara jarak jauh.

SLIDE 36

Immutable Backup

Write Once, Read Many (WORM)

Backup ditulis dengan penetapan polisi kebenaran (S3 Object Lock / Retention Lock). Selepas dicipta, TIADA SESIAPA — termasuk root admin — boleh memadam atau mengubah fail backup tersebut dalam tempoh masa terkunci (contoh: 30 hari).

SLIDE 37

Backup Encryption

Fail backup mengandungi keseluruhan rahsia perniagaan anda (Passwords, PII Users, DB dumps). Ia MESTI di-encrypt sebelum dihantar keluar.

Raw Data Dump
AES-256 Encrypted Payload
Public Cloud Storage
SLIDE 38

Encryption Key Management

Kehilangan Key = Kehilangan Data

Jika anda mempunyai 10TB backup ter-encrypt dengan sempurna, tetapi Passphrase / Private Key anda hilang semasa bencana server utama terbakar, backup itu TIDAK BOLEH DIPULIHKAN SAMPAI BILA-BILA!

Langkah Wajib: Simpan salinan Passphrase/Key di Password Manager terpisah & salinan fizikal ter-encrypt.

SLIDE 39

Backup Retention Policy

Menentukan berapa lama sesuatu fail backup disimpan sebelum dipadam secara automatik untuk menjimatkan ruang storage.

Contoh Polisi GFS (Grandfather-Father-Son):

Daily Backups: Simpan 7 Hari Terakhir

Weekly Backups: Simpan 4 Minggu Terakhir

Monthly Backups: Simpan 12 Bulan Terakhir

SLIDE 40

Impak Tempoh Retention

Senario: Silent Corruption / Pemadaman Senyap

Pengguna terpadam satu document secara senyap 2 minggu lepas, tetapi baru menyedarinya hari ini. Jika Polisi Retention anda hanya menyimpan 7 hari terakhir, SEMUA backup terkini mengandungi versi file terpadam! Retention lebih panjang (Monthly) diperlukan.

SLIDE 41

RPO (Recovery Point Objective)

"Berapa banyak kehilangan DATA yang sanggup anda tanggung?"

RPO diukur dalam julat MASA transaksi data.

• Jika Backup dijalankan setiap 24 Jam RPO anda = 24 Jam Data Loss.

• Jika Backup/Replication dijalankan setiap 15 Minit RPO anda = 15 Minit Data Loss.

SLIDE 42

RTO (Recovery Time Objective)

"Berapa lama DOWNTIME sistem yang anda sanggup terima?"

RTO ialah jumlah masa yang diambil dari saat bencana berlaku sehingga aplikasi sedia beroperasi semula.

• Memuat turun 5TB backup dari internet mengambil masa 8 Jam RTO minimum = 8 Jam Downtime.

SLIDE 45

Database Backup Strategy

Logical Backup (e.g. pg_dump)

Mengeksport struktur SQL schema & insert statements. Sangat mesra versi, tetapi agak perlahan untuk DB bersaiz Terabyte.

pg_dump -U postgres dbname > dump.sql

Physical Backup (e.g. pg_basebackup)

Menyalin terus blok fail biner database. Sangat pantas untuk DB bersaiz besar.

SLIDE 48

Rsync Caution: Mirroring vs Backup

rsync -av --delete /src/ /dest/
Flag `--delete` pada rsync akan memadam fail di destination sekiranya ia terpadam di source. Ini bukan Versioned Backup!

Untuk pemulihan bencana dan sejarah data terasing (Disaster Recovery & History).
