WHAT IS IDENTITY

Definisi Identity

Identity (Identiti)

Representasi digital yang unik bagi seseorang manusia, perkhidmatan (service), peranti (device), atau entiti perisian di dalam sesuatu sistem komputer.

Human Identity
bos@example.com

Representasi pemilik akaun manusia dengan atribut seperti e-mel, nama, dan peranan.

Service Identity
backup-service

Representasi bot atau skrip latar belakang yang memerlukan akses automatik.

Device Identity
laptop-admin-01

Representasi hardware fizikal yang dibenarkan berhubung ke server.

Nota Penting: Dalam dunia Self-Hosting & Production Architecture, Identity bukan semestinya hanya manusia!

AUTHENTICATION (AuthN)

Proses Pengesahan Identiti

"Siapa anda?"
  • Memeriksa maklumat log masuk (credentials).
  • Berlaku pada fasa awal sesi pengguna.
  • Contoh: Password, Passkey, OTP, Sijil.

Proses Kelulusan Hak Akses

"Apa anda boleh buat?"
  • Memeriksa peranan & peratus kebenaran.
  • Berlaku bagi setiap permohonan sumber/API.

Senario Contoh Dalam Realiti:

Seorang intern bernama Ali berjaya memasukkan password & MFA untuk masuk ke dashboard internal server. [Authentication: ✅ PASS]. Tetapi apabila Ali menekan butang DELETE DATABASE, sistem memaparkan mesej ralat 403. [Authorization: ❌ FAIL].

BASIC AUTHENTICATION

Username + Password

Mekanisme tradisional yang paling asas. Pengguna mengemukakan identifier unik (Username/Email) dan rahsia persendirian (Password).

Komponen Asas

Username: <USERNAME>
Password: <PASSWORD>

Mudah dilaksanakan pada peringkat pembangunan awal, tetapi mengandungi pelbagai risiko keselamatan disebabkan faktor tingkah laku manusia.

Cabaran & Kelemahan Risiko

  • Password Reuse: Pengguna mengguna semula password di banyak laman.
  • Weak Passwords: Kata laluan pendek yang mudah diteka.
  • Password Leaks: Kebocoran database pangkalan data lain.
  • Phishing: Pengguna terpedaya memasukkan password di laman palsu.

"Password masih digunakan secara meluas tetapi TIDAK BOLEH menjadi satu-satunya benteng keselamatan."

DATABASE SECURITY

Password VS Password Hash

JANGAN Simpan Plaintext

INSERT INTO users (email, password)
VALUES ('user@domain.com', 'secret123');

Jika database anda ditewaskan atau bocor, semua kata laluan pengguna akan terdedah secara terus!

SEBALIKNYA: Simpan Hash

Password Plaintext ('secret123')
↓ Cryptographic Hash Function
Stored Hash: $argon2id$v=19$m=65536...

Database menyimpan HASH sehala (one-way). Server membandingkan hash hasil input log masuk.

PERINGATAN KONSEP PENTING:

Hash ≠ Encryption!

Encryption adalah dua hala (boleh didokod semula dengan key). Hashing adalah fungsi sehala (one-way function) yang tidak boleh dinyahsulit semula.

HASH ENHANCEMENT

Salt (Garam Kriptografi)

Salt ialah nilai rawak unik yang dijana bagi setiap kata laluan sebelum fungsi hashing dijalankan.

Password + Random Salt → Password Hash Function → Stored Hash
User A (Password: "Rahsia123")
Salt: x8k9#mL
Hash: e3b0c44298fc1c149afbf4c8996fb...
User B (Password: "Rahsia123" - SAMA!)
Salt: pL2@9zQ
Hash: 8f4e002a2818c5e6d6105f24f0c...

Kenapa Perlu Salt?

Salt memastikan bahawa dua pengguna yang mempunyai kata laluan yang sama tidak akan mempunyai stored hash yang sama dalam pangkalan data. Ini menghalang penggunaan Rainbow Tables.

BEST PRACTICES

Password Hashing Algorithm

Bukan semua fungsi hash sesuai untuk menyimpan kata laluan. Kita memerlukan algoritma yang **perlahan (key stretching)** untuk mengekang serangan automatik.

DISYORKAN (Key-Stretching)

  • Argon2 (Argon2id) - Pemenang Password Hashing Competition. Sangat selamat & kalis GPU/ASIC.
  • bcrypt - Algoritma standard industri yang sangat meluas dan teruji.
  • scrypt / PBKDF2 - Pilihan sekunder untuk ketahanan memori tinggi.

JANGAN GUNA UNTUK PASSWORD

  • MD5 / SHA-1 - Algoritma usang yang telah ditewaskan secara kriptografi.
  • SHA-256 / SHA-512 (Sahaja) - Terlalu laju! Boleh dikira bilion kali sesaat menggunakan GPU moden.
CLIENT SECURITY

Password Manager

Alat utama untuk mengatasi isu kelemahan ingatan manusia dengan menjana dan menyimpan kata laluan terenkripsi secara automatik.

Generate Unique

Menjana password rawak berpanjangan tinggi (contoh: 32 karakter) bagi setiap laman web secara berasingan.

Encrypted Vault

Menyimpan kredensial dalam peti simpanan terenkripsi (Zero-Knowledge Architecture).

Autofill Protection

Mengisi borang secara automatik hanya pada domain yang tepat, mengurangkan risiko phishing domain tiruan.

[ Password Manager ] ──► Unique Complex Password ──► Every Service (Self-Hosted / Cloud)
MFA / 2FA

Multi-Factor Authentication (MFA)

MFA memerlukan sekurang-kurangnya dua faktor berbeza daripada kategori yang berlainan untuk mengesahkan identiti pengguna.

Factor 1: Knowledge

Something You Know

Kata laluan (password), PIN, atau soalan keselamatan.

Factor 2: Possession

Something You Have

Authenticator App (TOTP), Hardware Key (YubiKey), Peranti smartphone.

Factor 3: Inherence

Something You Are

Cap jari, pengecaman muka (Face ID), atau imbasan iris.

Password (Something You Know) + Authenticator Code (Something You Have) = MFA ✅
RFC 6238

Time-Based One-Time Password (TOTP)

TOTP menggunakan rahsia bersama (Shared Secret Key) dan masa semasa (Current Timestamp) untuk menjana kod 6-digit yang bertukar setiap 30 saat.

Cara Kerja:

  1. Server & App berkongsi Secret Key (QR Code).
  2. Kedua-dua mengira HMAC-SHA1 menggunakan unix time.
  3. Kod 6-digit dihasilkan secara selari tanpa perlu sambungan internet.
Aplikasi Authenticator Contoh
849 201

Berubah secara automatik setiap 30 saat.

Peringatan Penting: TOTP bukan sama dengan kata laluan kedua yang kekal. Kod TOTP hanya sah sekali sahaja (One-Time).
HARDWARE SECURITY

Hardware Security Key

Peranti fizikal khas (seperti YubiKey / Nitrokey) yang menyimpan kunci kriptografi secara selamat di dalam cip mikro khas (Secure Element).

Physical Possession

Pengguna mesti memegang kunci fizikal dan menyentuh peranti untuk mengesahkan log masuk.

FIDO2 / WebAuthn

Menggunakan piawaian terbuka yang terikat pada domain aplikasi secara terperingkat.

Phishing Resistant

Tidak boleh ditipu oleh laman web palsu kerana penyemak laluan browser menyemak origin domain.

User ──► Insert Security Key & Touch ──► Cryptographic Proof Sent ──► Server Authenticated ✅
MODERN AUTHENTICATION

Passkey (FIDO2 Standard)

Passkey ialah pengganti kata laluan masa hadapan berasaskan kunci kriptografi awam/peribadi (Public/Private Key Pair) yang terikat pada peranti pengguna.

Kelebihan Utama Passkey

  • Phishing-Resistant: Terikat secara automatik dengan domain asal (origin binding).
  • No Passwords: Tiada kata laluan untuk diingat, dicuri atau dibocorkan.
  • Biometric Fast: Disahkan menggunakan Touch ID, Face ID, atau PIN peranti.

Mekanisme Kriptografi

Private Key ──► Kekal Selamat Dalam Device
Public Key ──► Disimpan Di Server Aplikasi

Challenge ──► Signed by Device ──► Verified by Server
Nota Penting: Pelaksanaan passkey berbeza mengikut ekosistem (iCloud Keychain, Google Password Manager, Bitwarden).
STATE MANAGEMENT

Session (Sesi Pengguna)

Protokol HTTP adalah stateless (tidak mengingati permintaan sebelumnya). Session digunakan untuk mengekalkan keadaan log masuk pengguna dari semasa ke semasa.

Aliran Mewujudkan Sesi:

1. User Log Masuk
2. Server Hasilkan Session ID
3. Simpan di Redis / Database
4. Hantar Session Cookie ke Browser

Stateful Session

Server menyimpan maklumat sesi dalam memori/database (cth: Redis). Mudah dibatalkan (revoke) serta-merta.

Stateless Session

Data sesi disimpan dalam token terenkripsi/tertandatangan yang dipegang oleh client (cth: JWT Cookie).

BROWSER STORAGE

HTTP Cookie

Cookie ialah cebisan data kecil yang dihantar oleh server kepada pelayar web (browser) pengguna, dan dihantar semula secara automatik dalam setiap permintaan berikutnya.

Fungsi Utama Cookie

  • Membawa Session Identifier untuk mengesahkan identiti.
  • Menyimpan tetapan keutamaan pengguna (Theme, Language).
  • Dihantar secara automatik oleh browser ke domain berkenaan.

Peringatan Keselamatan

Kerana cookie membawa identiti sesi log masuk anda, ia mestilah dilindungi menggunakan atribut keselamatan yang ketat bagi mengelakkan dicuri melalui skrip bahaya (XSS) atau dipintas melalui rangkaian terbuka.

HARDENING

Secure Cookie Attributes

Tiga atribut kritikal yang WAJIB ditetapkan pada setiap session cookie pengeluaran:

Secure

Memastikan cookie HANYA dihantar melalui sambungan terenkripsi HTTPS. Tidak akan dihantar melalui HTTP biasa.

HttpOnly

Menghalang skrip JavaScript pelayar (document.cookie) daripada membaca cookie ini. Melindungi daripada XSS.

SameSite=Lax / Strict

Mengawal sama ada cookie dihantar bersama permintaan rentas laman (cross-site). Membantu mengekang serangan CSRF.

Set-Cookie: session_id=<TOKEN>; Secure; HttpOnly; SameSite=Lax; Path=/;
LIFECYCLE CONTROL

Session Expiration (Penamatan Sesi)

Sesi yang bertahan selamanya tanpa tamat tempoh adalah satu risiko keselamatan yang besar.

1. Idle Timeout (Masa melahu)

Sesi dibatalkan sekiranya tiada aktiviti daripada pengguna dalam jangka masa tertentu (contoh: 15 minit tanpa klik).

2. Absolute Timeout (Masa mutlak)

Sesi dibatalkan secara paksa selepas tempoh maksimum (contoh: 8 jam), walaupun pengguna masih aktif menggunakannya.

Aliran Tamat Sesi:
Login ──► Active Session ──► Idle / Max Time ──► Session Expired ──► Redirect to Login
API AUTHENTICATION

Access Token

Access Token ialah bukti kelayakan digital yang dikeluarkan oleh Authorization Server untuk membenarkan client mengakses API atau sumber tertentu bagi pihak identiti.

Ciri-Ciri Access Token

  • Berjangka hayat pendek (Short-lived, contohnya 15-60 minit).
  • Mempunyai skop kebenaran khusus (Scoped Permissions).
  • Biasanya dihantar melalui HTTP Header: Authorization: Bearer <TOKEN>

Peringatan Penting

Access token bukannya mewakili keseluruhan identiti pengguna secara kekal, sebaliknya ia hanyalah tikat kebenaran terhad untuk membuat tindakan tertentu.

TOKEN MANAGEMENT

Refresh Token

Credential berjangka hayat panjang yang digunakan khusus untuk meminta Access Token baharu apabila access token sedia ada telah tamat tempoh.

Aliran Pembaharuan Token:

1. Access Token Expired (401)
2. Client hantar Refresh Token
3. Auth Server Semak & Sahkan
4. Terima New Access Token

Access Token

Hayat Pendek (15 minit). Disimpan dalam ingatan sementara.

Refresh Token

Hayat Panjang (7-30 hari). Disimpan secara selamat (HttpOnly Cookie / Secure Storage).

RFC 7519

JSON Web Token (JWT)

JWT ialah format token standard terbuka yang padat dan bersendirian (self-contained) untuk menghantar maklumat JSON secara tertandatangan antara dua pihak.

1. Header

{"alg": "RS256", "typ": "JWT"}

Jenis token & algoritma tandatangan.

2. Payload

{"sub": "123", "name": "Ali", "role": "admin"}

Claims / data identiti & kebenaran.

3. Signature

HMACSHA256(base64(Header) + "." + base64(Payload), secret)

Pengesahan integriti data.

AMARAN KESELAMATAN JWT: JWT secara lalai HANYA TERTANDATANGAN (signed), BUKAN TERENKRIPSI! Sesiapapun boleh membaca kandungan Payload jika di-decode Base64. Jangan simpan password atau rahsia di dalam JWT Payload!
DATA STRUCTURE

JWT Claims Standard

Claims ialah kenyataan mengenai entiti identiti yang disimpan di dalam JWT Payload:

sub (Subject)

ID unik entiti identiti pengguna (cth: "usr_99812").

iss (Issuer)

Pihak pengeluar token (cth: "https://auth.example.com").

aud (Audience)

Penerima token yang disasarkan (cth: "https://api.example.com").

exp (Expiration Time)

Masa luput token dalam format Unix Timestamp.

iat (Issued At)

Masa token dikeluarkan dalam format Unix Timestamp.

nbf (Not Before)

Masa mula token sah diproses.

AUTHORIZATION FRAMEWORK

OAuth 2.0 Framework

PERINGATAN PENTING:

OAuth 2.0 BUKAN "Protocol Log Masuk" (Authentication Protocol)!

OAuth 2.0 ialah Authorization Framework yang membolehkan aplikasi pihak ketiga memperoleh akses terhad kepada sumber pengguna tanpa mendedahkan kata laluan.

Tujuan Utama OAuth

Membenarkan pengguna memberikan kebenaran (Delegated Authorization) kepada App A untuk membaca file di Server B tanpa memberikan kata laluan Server B.

Hasil OAuth

Client menerima Access Token berhad dengan skop yang diluluskan (cth: read-only access to drive files).

ARCHITECTURE ROLES

4 Peranan Utama OAuth 2.0

1. Resource Owner

Pengguna (manusia) yang memiliki data atau sumber dan memberikan kebenaran akses.

2. Client Application

Aplikasi yang ingin mengakses sumber bagi pihak Resource Owner (cth: Web App anda).

3. Authorization Server

Server yang mengesahkan identiti pengguna dan mengeluarkan Access Token (cth: Keycloak, Authelia).

4. Resource Server

Server API yang menyimpan data terlindung dan menerima Access Token yang sah.

AUTHENTICATION LAYER

OpenID Connect (OIDC)

OpenID Connect (OIDC) ialah lapisan identiti (Identity Layer) yang dibangunkan di atas rangka kerja OAuth 2.0 untuk menyediakan fungsi **Authentication**.

OAuth 2.0

Hanya menjaga AUTHORIZATION (Access Token).

OpenID Connect (OIDC)

Menambah AUTHENTICATION dengan memperkenalkan ID Token (JWT).

ID Token (OIDC Payload Contoh)

{
  "iss": "https://auth.example.com",
  "sub": "user_10293",
  "email": "bos@example.com",
  "email_verified": true
}

ACCESS CONTROL MODEL

Role-Based Access Control (RBAC)

Model pengawalan akses di mana kebenaran (permissions) dikelompokkan ke dalam **Peranan (Roles)**, dan pengguna ditetapkan ke dalam peranan tersebut.

User (Ali)
Role (Editor)
Permissions (Read, Write)
Admin Role

user:create, user:delete, system:config, content:write

Editor Role

content:create, content:update, content:read

Viewer Role

content:read

PRACTICAL SCENARIO

Contoh Penguatkuasaan RBAC

Ali

Pengguna: Ali

Role Terikat: Editor

✅ Kebenaran Dibolehkan:
  • Read Content
  • Create New Article
  • Update Drafts
❌ Kebenaran Ditolak (Denied):
  • Delete Users
  • Manage Billing & Invoices
  • Modify Server Firewall
ADVANCED ACCESS CONTROL

Attribute-Based Access Control (ABAC)

Model kawalan akses dinamik yang membuat keputusan berdasarkan Atribut Komprehensif (Pengguna, Peranti, Jaringan, Masa, & Sumber).

Contoh Logic Polisi ABAC:

IF user.role == "admin"
AND device.managed == true
AND context.time BETWEEN 08:00 AND 18:00
AND request.location == "MY"
THEN
  ALLOW ACCESS
ELSE
  DENY (403 Forbidden)
Perbandingan Model

RBAC VS ABAC

RBAC (Role-Based)

  • Berdasarkan Peranan Statik (Role → Permission).
  • Mudah disediakan & diuruskan untuk perniagaan kecil.
  • Kekurangan: Sukar menyesuaikan dengan keadaan kontekstual dinamik.

ABAC (Attribute-Based)

  • Berdasarkan Atribut Dinamik (Attributes → Policy → Decision).
  • Sangat fleksibel (mengambil kira lokasi, peranti, masa).
  • Kekurangan: Kompleks untuk dibina dan diselenggara.
SECURITY PRINCIPLE

Principle of Least Privilege (PoLP)

Prinsip Keizinan Minimum

Setiap entiti identiti (manusia atau perkhidmatan) HANYA diberikan tahap kebenaran minimum yang betul-betul diperlukan untuk menjalankan tugasnya, dan tidak lebih daripada itu.

❌ Amalan Bahaya:

Memberikan kebenaran Administrator / Root kepada semua pembangun atau perkhidmatan script.

✅ Amalan Selamat:

Mewujudkan akaun khusus mengikut peranan (Viewer, Editor, Backup Agent) dengan hak akses terhad.

Amalan Terbaik: Guna kredensial berasingan, buat pusingan kunci (rotation), dan aktifkan logging khas untuk Service Accounts.

IF user.email ENDS_WITH "@company.com"
AND user.mfa_satisfied == true
AND user.country == "MY"

ACTION: ALLOW
ELSE ACTION: BLOCK

Mekanisme ini menyaring trafik sebelum paket data sampai ke pelayan infrastruktur anda.

Prinsip Zero Trust Identity

"Never Trust, Always Verify."

Jangan sesekali menganggap trafik di dalam rangkaian dalaman (Internal Network) adalah selamat secara automatik.

CONTEXTUAL SECURITY

Device Identity

Identity bukan hanya terikat pada pengguna manusia, tetapi juga mengambil kira status dan identiti peranti yang digunakan.

Semakan Status Peranti (Device Health Check)

  • Adakah peranti diuruskan oleh syarikat (Managed Device)?
  • Adakah OS mempunyai kemaskini keselamatan terkini?
  • Adakah disk dienkripsi (BitLocker / FileVault)?

Peringatan Zero Trust

Akses dari peranti yang tidak dikenali atau dijangkiti malware boleh dibatalkan secara automatik walaupun kata laluan pengguna adalah sah.

Lengkap: Authorization Flow

1. User Alice (Role: Editor) memohon: DELETE /api/users/123
2. Web Server menyemak token identiti Alice: Identity Valid ✅
3. Web Server menyemak kebenaran Role Editor: Editor cannot delete users ❌
RESULT: HTTP 403 Forbidden Response
HTTP STATUS CODES

401 Unauthorized VS 403 Forbidden

HTTP 401

Unauthorized (Unauthenticated)

Sistem tidak mengenali siapa anda. Anda belum log masuk atau token tidak sah.

→ "Who are you? Please log in."
HTTP 403

Forbidden (Unauthorized Action)

Sistem tahu siapa anda, tetapi anda TIDAK MEMPUNYAI KEBENARAN untuk membuat tindakan itu.

→ "I know who you are, but you can't do this."
